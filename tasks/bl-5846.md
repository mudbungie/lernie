## Concern
The workspace-wide startup scan (§2.11) runs at every driver invocation — with the §6 exec baton, every hop of every chain re-sweeps every branch, and the scan's inbox flush launches drivers that themselves scan. Frequency is matched to step rate; the events it compensates for happen at crash rate. O(branches) per spawn, driver-launching-driver recursion.

## Baseline: the minimal design carries normal operation (user-confirmed)
The front door alone is self-propagating: `lernie message` (1) deposits, (2) probes the executor lock, (3) launches a driver if quiescent; the executor drains its inbox at every step boundary. Deposit-before-probe ordering means a queued item exists before anyone checks. Every terminal event deposits (§2.3 step 5 is total), so the healthy path needs zero scanning and zero inbox-watching.

## Graceful-exit race and its closure (user-confirmed 2026-07-12)
The one crack in the minimal design: a deposit landing after the executor's last inbox read but before its lock release — the writer's probe sees the lock held (no launch), the executor never looks again. Both sides conclude the other has it. Closure is symmetry with the writer's act-then-check: the executor's exit path is **drain → release lock → list inbox → launch-if-pending** (it cannot drain after release; it launches like a writer). Every deposit is then covered: before final drain → drained; before release → post-release list launches; after release → the writer's own probe sees a free lock and launches. Redundant launches are arbitrated by the flock (loser is a clean no-op). inotify is NOT the mechanism: holding the fd confers no notifications, and inotify queues can overflow — it may serve as a mid-loop latency optimization, never as correctness (same advisory status as §3.1 frontend watching).

## Crashes: accepted as a failure class (user decision 2026-07-12)
Uncatchable death (SIGKILL/OOM/panic/reboot) strands (a) a dead child's undeposited result — parked parent waits until next touch; (b) messages deposited while the doomed executor lived. Decision: treat crashes as crashes. Everything is on disk, so nothing is lost, only late; the next touch heals (a user reprompt, or `lernie scan` run by hand / cron if an operator wants a heartbeat). Rationale: auto-healing exacerbates the worst failure modes — a janitor relaunching the runaway agent an operator is trying to kill. So the janitor verb is an OPERATOR tool, never wired into any hot path or default schedule.
