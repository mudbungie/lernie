`prompt/budget/derive.rs::usage_tokens` sums all four brazen `Usage`
counters unconditionally:

    Event::Usage(u) => opt(u.input_tokens) + opt(u.output_tokens)
                     + opt(u.cache_read_tokens) + opt(u.cache_write_tokens)

ARCH §6 states the rule as "the four `Usage` counters summed". That is
correct only where the counters are **disjoint slices** of one prompt.
They are not disjoint on every provider, and brazen says so on purpose —
its canonical `Usage` is deliberately unnormalized because providers
disagree about overlap:

- `protocol/openai/decode/mod.rs` maps `input_tokens = usage.prompt_tokens`
  and `cache_read_tokens = usage.prompt_tokens_details.cached_tokens`.
  `cached_tokens` is a **subset of** `prompt_tokens`, not a sibling of it.
- `protocol/openai_responses/decode/terminal.rs` is the same shape
  (`input_tokens` / `input_tokens_details.cached_tokens`).
- `protocol/google_genai/decode/mod.rs` likewise
  (`promptTokenCount` contains `cachedContentTokenCount`).
- Anthropic is the shape the rule assumes: the three are disjoint.

So on an OpenAI- or Google-shaped provider the cached slice is billed
twice, and the inflation grows with the cache hit rate — i.e. it is worst
exactly where a long conversation is cheapest.

**Measured on a live root conversation** (52 transcript entries, 8
dispatched subagents, 24 steps across the tree, worker on an
`openai-chatgpt` provider row). One step's usage line, verbatim:

    {"type":"usage","input_tokens":93556,"output_tokens":132,
     "cache_read_tokens":91648,"cache_write_tokens":null}

`usage_tokens` bills 185,336 for a prompt of 93,556.

Whole tree:

| derivation | tokens |
|---|---|
| `derive::spend` as shipped | 2,248,984 |
| overlap-corrected `max(input, cache_read + cache_write) + output` | 1,796,888 |
| phantom | 452,096 (+25%) |

That workspace's config carried `max_total_tokens: 2000000`, so the
harness wrote `refs/lernie/budget-exhausted/<root>`, deposited a
`budget-exhausted` epitaph with no body and ceased the branch **at a
`tool_result` tail** — the conversation had done the work and was one
model call from answering. Corrected, the tree was at 1.80M and had
headroom: the double count is what ended it.

Three consequences, in falling order of harm:

1. A declared ceiling ends conversations earlier than its number reads,
   by a factor that depends on an implementation detail of the provider's
   usage block. bl-8dea already took the shipped default off; this is the
   arithmetic underneath the number an operator who declares one gets.
2. Every downstream reader inherits it. yog's `budgets::BudgetSpend::
   total_tokens` mirrors this sum *deliberately*, to show the figure that
   exhausts the ceiling, and then prices each counter at its own
   per-million rate — so the cached slice is charged once at the input
   rate and again at the cache-read rate, inflating a dollar figure and a
   spawn gate keyed to it.
3. `max_total_tokens` is not comparable across providers, so the same
   number means different conversation lengths on different rows.

**The fix is not "sum three instead of four".** Which counters overlap is
a per-protocol fact and brazen is the only crate that knows it. Two
shapes, both open:

- Normalize in brazen: have each decoder emit disjoint slices (an
  OpenAI-shaped decoder subtracting `cached_tokens` out of
  `input_tokens`), leaving §6's "sum the four" true everywhere. One
  change, every consumer fixed, but it rewrites a published canonical
  contract that currently promises the provider's own numbers unaltered.
- Or fold defensively in lernie: `max(input, cache_read + cache_write) +
  output`, which is exact where the slice is contained, degrades to
  plain `input_tokens` where no cache counters are reported, and is a
  floor (never an over-statement) where they are disjoint. This is
  already the formula yog uses for context fullness, for exactly this
  reason. Cheaper and local; leaves the same fix owed to every other
  consumer.

Either way ARCH §6's "the four `Usage` counters summed" needs to state
the overlap rule rather than assume disjointness, and a fixture per
provider shape should pin it.
---

**Settled: fold defensively here, and file the contract question upstream.**

Shipped in `prompt/budget/derive.rs::usage_tokens`:

    let cached = opt(u.cache_read_tokens) + opt(u.cache_write_tokens);
    opt(u.input_tokens).max(cached) + opt(u.output_tokens)

Why this and not the brazen normalization, checked against the pinned
adapter's own source rather than assumed:

- brazen documents nothing about overlap. `specs/architecture.md` §3.2
  says only that every counter is `Option` and never a fabricated `0`,
  and that the fields map from each provider's own names — i.e. the
  contract is "the provider's numbers unaltered", which neither promises
  disjointness nor forbids the sum. So the sum was not violating a
  documented contract; it was reading one that does not exist. The
  overlap is real at all five decode sites: `anthropic` disjoint,
  `openai` / `openai_responses` / `google_genai` contained,
  `ollama_chat` reporting no cache counters at all.
- The harness genuinely cannot tell which shape it holds. A step record
  carries `commit` / `started_at` / `ended_at` and nothing else — no
  protocol, no provider row — and the `Usage` event names neither. A
  provider-keyed table here would be brazen's routing knowledge copied
  into the harness, which is the coupling the adapter exists to prevent.
- So the fold takes the larger of the two readings of the prompt rather
  than their sum: exact where the slice is contained, a **floor** where
  the counters are disjoint (it drops whichever of the uncached and
  cached halves is smaller), and plain `input + output` where no cache
  counter is reported. A floor, not a ceiling, on purpose — the failure
  this ball is about is a phantom token ending a conversation before the
  operator's declared limit.

**Filed upstream: brazen bl-d192**, with the three shapes laid out —
normalize the decoders (the sum becomes true everywhere, but it is a
`v=1` semantic change to an existing value), document the overlap
per-protocol *and* surface which shape applies, or add a decoder-computed
`total_tokens` (additive under `v=1`, no protocol on the wire). This fold
collapses back to a plain sum the day the first lands, and the doc
comment on `usage_tokens` says so by id.

**Also checked, and clean:** no other lernie site folds the four counters
into a total. `crates/agent-eval` (`metrics.rs`, `report.rs`,
`compare.rs`) aggregates each counter separately and never adds them up,
and `prompt/dispatch/entry.rs::UsageReport::fold` carries the provider's
counters through verbatim onto the transcript entry — both correct as
they stand. yog's mirror of the fold is its own ball (yog bl-6621),
downstream on purpose.

ARCH §6 now states the overlap rule where it used to assume
disjointness, §8's metering bullet points at it, and two fixtures pin
both shapes (`spend_bills_a_contained_cached_slice_once`,
`spend_counts_disjoint_cache_counters_beside_a_smaller_prompt`).
