## Verdict (Gorse, 2026-07-25): hypothesis disproven. Closed with the
## investigation recorded; no production change.

The upstream mechanism described below is real in the pinned toolchain
(llvm_profparser 0.10.0, which cargo-tarpaulin 0.35.2 depends on — read
from the published sources). It is **structurally unreachable in this
repo**, so there is nothing to mitigate and nothing to file upstream that
would change our numbers.

### What was measured

Reproduced tarpaulin's exact pool arrangement by hand — build with
`RUSTFLAGS=-C instrument-coverage`, then run the lib test binary with
tarpaulin's own pattern
`LLVM_PROFILE_FILE=<pool>/<test-binary>_%m-%p.profraw`.

1. **Pool pollution is real.** The pool ends up holding the test
   binary's own profraw *plus one per spawned `lernie` process* (3
   spawns of the `bash_tool` module -> 4 files, distinct `%m`
   signatures, pid-carrying names). Same for `tests/config_cli` (1 + 4).
   So the premise holds: two different binaries write into one pool and
   `merge_profiles` parses them in `WalkDir` order.

2. **The merge cannot misattribute.** `llvm-profdata show
   --all-functions` on the test-binary profraw and on a `lernie`-binary
   profraw, intersected by function name:

   - test binary: 17497 records; `lernie` binary: 5473 records
   - shared names: **3133**
   - shared names mentioning `lernie`: **0**
   - shared names with differing structural hash: **0**
   - shared names with differing counter count: **0**

   The reason is the crate disambiguator. The lib compiled `--cfg test`
   and the lib linked into the `lernie` bin are different compilations
   with different `-C metadata`, so every repo symbol differs. The
   function behind the original sighting is the clean example:

       test binary:  _RNvNtNtCs5GBNLOVA7gO_6lernie6prompt6budget5check
                     Hash 0xb8cdc7aa5c20776f, Counters 7
       lernie bin:   _RNvNtNtCslo6p4TyE50k_6lernie6prompt6budget5check
                     Hash 0x70ec4cbeb99c7954, Counters 7

   Different names => `find_record_by_name_mut` never returns the
   foreign record => `InstrProfRecord::merge`'s
   `if self.counts.len() != other.counts.len() { return; }` silent drop
   can never fire on repo code, and base-record order (WalkDir/pid) is
   irrelevant. The 3133 names that *do* collide are all dependency/std
   monomorphizations instantiated identically in both images: same hash,
   same counter count, so the merge sums and never drops — and those
   files are outside the reported root anyway
   (`generate_subreport(|paths| paths.starts_with(root))`).

3. **`tests/*` integration binaries are clear too.** `tests/config_cli`
   carries 76 instrumented records, none of them lernie-lib code (it
   only spawns the binary and uses `tempfile`); shared names with the
   `lernie` bin: 0.

### The corollary worth keeping

`CoverageMapping::new(&binaries, &instrumentation, true)` is handed only
the binaries tarpaulin *launched* — the test binary, plus `--objects`
extras we do not use. A merged record whose name matches nothing in that
coverage map is simply ignored. So a spawned `lernie`'s execution
contributes **nothing to the numerator**: every counted line needs an
in-process test. `tarpaulin.toml` previously said \"the production code
they exercise stays fully counted\", which reads the other way; corrected
there, with the measurement recorded so nobody re-derives it (5844532).

By the same token the mitigation this ball proposed — scrubbing
`LLVM_PROFILE_FILE` at the e2e spawn seam — is coverage-neutral: it
would change no numerator and no denominator. Pure added mechanism, so
it was not done. The cargo-llvm-cov migration posture is unaffected by
this ball either way; it is a separate denominator question.

### What this does NOT explain

The `src/prompt/budget/mod.rs:127` sighting is still unexplained. Ruled
out by the above: cross-binary counter misattribution. Also worth noting
the line is covered by an ordinary in-process unit test
(`src/prompt/budget/tests/enforce.rs:93`, the `Axis::Depth` assertion)
under `--test-threads=1`, so the execution side is deterministic. If it
recurs, capture `target/tarpaulin/profraws/` before tarpaulin exits —
without the artifacts there is no further inference to make.

### The hazard (read from tarpaulin 0.35.2 + llvm-profparser sources)

Tarpaulin's llvm engine sets `LLVM_PROFILE_FILE=<target>/tarpaulin/profraws/<test-binary>_%m-%p.profraw`
for each test binary (`src/process_handling/mod.rs:273`). Every subprocess a test
spawns **inherits that variable**, so the instrumented `lernie` binary our e2e
tests drive writes its own profraws into the same pool. After the test binary
exits, tarpaulin merges every new profraw in that pool
(`src/statemachine/instrumented.rs`, `merge_profiles`) and maps the result
through the *test binary's* coverage map alone.

The merge is keyed by function NAME, not by the structural hash:

- `InstrumentationProfile::merge_record` looks the record up with
  `find_record_by_name_mut` (llvm-profparser `src/instrumentation_profile/types.rs`);
- `InstrProfRecord::merge` starts with `if self.counts.len() != other.counts.len() { return; }`
  — a same-named record whose counter vector differs in length is silently
  discarded, no warning;
- `CoverageMapping::get_simple_counters` binds a function's regions to
  `find_record_by_hash` -> symtab name -> `find_record_by_name`, i.e. by name again.

Whichever profraw `merge_profiles` parses FIRST becomes the base record for a
name. The parse order is the `WalkDir` order of the profraw directory, and the
filenames carry `%p` (pid), so the order changes from run to run with no code
change.
