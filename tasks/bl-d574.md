Material that is present, valid and correctly permissioned, but filed in a
directory under `wire/workspaces/` whose name is not a workspace the operator
then asks for, is reported as material that does not exist:

    $ lernie entries
    (this box's own engine)
        nothing provisioned at …/lernie/wire
    <some-name>
        <the address stated>

    $ lernie conversations <a-workspace-that-does-exist>
    lernie: no wire provisioned at …/lernie/wire: the pair is minted on the
    host that issued it (`yog wire-certs WIRE_LEAF=<name>` there) and carried
    here by hand; the seat mints nothing

**The diagnosis is wrong and its remedy is destructive of the operator's
time.** Nothing needs minting. A channel is provisioned and `entries` has just
listed it; it simply sits under a name no gesture routes to, and the fix is a
`mv`. The sentence instead sends the operator back to the box that holds the
CA to issue a second leaf, which will land in the same wrong directory and
fail identically.

The refusal is reasoning from the wrong subject. `conversations <ws>` failed to
find a channel named `<ws>`, so it fell back to this box's own engine slot at
`wire/`, found that unprovisioned, and reported *that* — a true sentence about
a directory the operator never asked about. The question was "where is the
channel for `<ws>`", and the answer names `wire/`.

This is reachable by an operator doing exactly as they were told: yog's
`wire-certs` closes by instructing them to file the material under the LEAF's
name (`wire/workspaces/<leaf>/`), which is never a workspace name. That half is
filed in yog's store as bl-686c; this half is the seat's, and stands on its own
regardless of how the directory came to be misnamed — a typo reaches it just as
well.

What is wanted: when a named channel is not found, the refusal should be about
the name that was asked for, and should say what channels DO exist — the
information `entries` already computes. A channel present under an unrouted
name is the likely cause and the remedy is renaming it; "nothing is
provisioned" should be reserved for the case where nothing is.

Found while provisioning a new device against a deployed engine.

## Re-driven on 0.1.0: the worse face is when the flat channel IS provisioned

The fallback this ball names is intentional and documented —
`crate::seat::route`'s own test is titled *"an unaddressed gesture goes to the
flat root"* and its doc says that is *"where every name no entry holds goes
too."* This ball is right that the CONSEQUENCE is wrong, and there is a second
consequence that is worse than the misleading refusal.

**Where the flat channel is provisioned and up, a name no entry holds is not
refused at all.** Driven against a box holding a flat channel plus two entries:

    $ lernie ask '{"op":"workspaces","workspace":"NoSuchWs"}'
    {"kind":"workspaces","ok":true,"rows":[…this box's own engine's roster…]}
    $ echo $?
    0

An `ok` answer, exit 0, from a channel the operator did not name, about a
workspace that does not exist. The engine's `workspaces` op does not read the
`workspace` field, so nothing downstream catches it either. Where the op DOES
read the name the engine refuses — `lernie conversations NoSuchWs` answers
`unknown workspace "NoSuchWs"` at exit 1 — but that refusal is the FLAT
engine's opinion about a name the operator may have meant for a different one,
and the seat never says which engine answered.

The two faces are one fact: **the seat resolves a name against its entries, and
when it finds nothing it substitutes a different destination instead of saying
so.** Whether that shows up as a wrong sentence (this ball's case, flat absent),
a wrong engine's refusal, or a successful answer from somewhere nobody asked
(above) is a matter of what the flat slot happens to hold.

That makes the remedy this ball already proposes stronger, not different: when a
named channel is not found, the refusal is about the name that was asked for and
names the channels that DO exist. It also wants a decision the ball does not yet
take — whether an envelope that NAMES a workspace should fall through to the
flat channel at all, or whether the fallback belongs only to the envelope that
names none.

The rename path is unaffected and works: an entry carrying a `workspace` file is
listed as `<leaf> (named "<host name>" on its host)`, routes down its own
channel, and crosses in the host's spelling — including inside a nested `target`
(the bl-4a36 fix, driven live on this binary).
