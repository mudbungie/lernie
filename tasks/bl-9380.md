FINDING, not a plan — this ball records a measured blocker so nobody spends the
afternoon rediscovering it, and states the one route that is left.

CONTEXT. yog bl-888d put the macOS builds on the same reproducible container
line as the Linux images (yog DESIGN Section 10 and 10.1). It landed for the foot
(thrall bl-e479) and for the engine and its adapter (litany bl-c2b9). It
CANNOT land here, and the reason is structural rather than a missing flag.

WHAT WAS MEASURED. The seat cross-compiles cleanly for `aarch64-apple-darwin`
under the same pinned toolchain the other two use — every crate in the graph
COMPILES, `eframe`, `egui`, `winit`, `glutin`, `glow`, `arboard` and the
`objc2` family included. The build dies at the LINK step, on the very last
step, with:

    error: unable to find dynamic system library 'objc' using strategy
    'paths_first'

and behind it the rest of the same wall, which the rustc link line asks for in
order: `-framework OpenGL`, `AppKit`, `CoreGraphics`, `Foundation`,
`CoreFoundation`, `ApplicationServices`, `CoreVideo`, `Carbon`, and `-lobjc`.

WHY NO FLAG FIXES IT. The cross toolchain is zig cc, and zig ships exactly ONE
darwin stub — `lib/libc/darwin/libSystem.tbd` — and no framework stubs at all.
A crate graph that links only libSystem crosses; one that links any Apple
framework does not, and the frameworks live only in Apple's SDK.

WHY THE SDK IS NOT THE ANSWER. The Xcode and Apple SDKs Agreement refuses it
twice, and either clause alone would settle it. Section 2.7: "The grants set forth
in this Agreement do not permit You to, and You agree not to, install, use or
run the Apple Software or Apple Services on any non-Apple-branded computer or
device, or to enable others to do so. ... You agree not to rent, lease, lend,
upload to or host on any website or server, sell, redistribute, or sublicense
the Apple Software and Apple Services, in whole or in part, or to enable others
to do so." Section 2.5: "You are expressly prohibited from separately using the Apple
SDKs or attempting to run any part of the Apple Software on non-Apple-branded
hardware." The first forbids the SDK sitting in this repo or in anything
published from it; the second forbids the usual escape of taking an SDK path as
a build argument, because a Linux builder is not Apple-branded hardware. So
osxcross is not held at arm's length here — the whole arm is refused, and a
Containerfile with an SDK input would be inviting an operator into a term they
cannot satisfy.

WHAT IS LEFT, and it is the honest recommendation. The seat's mac artifact
comes off APPLE HARDWARE or it does not come at all: a macOS runner in CI,
which is where yog already runs its own macOS leg (yog DESIGN Section 10, the
`macos.yml` workflow that reports without holding the release gate). Two things
that route must answer and this ball does not: whether the CI provider's mac
hardware satisfies "owned or controlled by You" under section 2.2.A is the operator's
question, not an implementer's; and a downloaded artifact carries a quarantine
attribute, so signing and notarization are acts on a mac by whoever publishes,
not something a build line can do for them.

WHAT NOT TO DO. Do not add an SDK path, a vendored `.tbd`, or a "just this once"
framework stub. Do not reach for a different Linux cross toolchain — the
constraint is Apple's licence, not zig's feature set, so a toolchain that
succeeded would be one that had acquired the SDK. If the seat's window is ever
made optional behind a feature, a headless wire-client artifact WOULD cross by
the thrall rule (libSystem only), and that is a different ball with a different
product.

SHAPE TO COPY IF THIS IS EVER UNBLOCKED: thrall bl-e479 and litany bl-c2b9 both
carry a `Containerfile.mac`, a `make mac-artifact` target and a
`scripts/mac-verify.sh` that READS the produced Mach-O (architecture, filetype,
LC_BUILD_VERSION, code signature, every LC_LOAD_DYLIB) instead of trusting the
build, with a negative direction that must refuse malformed inputs first.
Whatever produces a mac seat should be verified the same way, and should state
what is proven versus merely built.

---

OPERATOR RULING, and it settles the open question this ball left. The question was section 2.2.A's "owned or controlled by You" over a CI provider's mac hardware, and the answer is that a GitHub Actions macOS runner IS Apple-branded hardware in the licence's sense: the Apple software runs on an Apple machine, which is exactly what sections 2.5 and 2.7 exist to require. So the route this ball called the honest recommendation is not merely the one left — it is the one taken.

THE REMEDY IS THEREFORE A JOB, NOT A TOOLCHAIN. The seat's mac artifact is a `macos` job in the release workflow, running on a mac runner, building natively with the platform SDK already on the image. Nothing in this repo acquires, vendors or paths to an SDK; nothing cross-compiles darwin from Linux. The WHAT NOT TO DO section stands unchanged and is now load-bearing rather than cautionary — a Linux cross toolchain that succeeded would be one that had acquired the SDK, and no job on a mac runner ever needs one.

WHAT THIS DOES NOT SETTLE. Signing and notarization still are not a build-line act: a downloaded artifact carries a quarantine attribute, and clearing it is a credentialled act by whoever publishes. And the mac job's verification should be the shape this ball already names — read the produced Mach-O rather than trust the build, with a negative direction that refuses malformed input first — rather than the Containerfile half of it, which no longer applies.

This ball stays open as the finding; the job lands with the release workflow, which is filed separately.
