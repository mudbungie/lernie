## The argument to write down (from the 2026-07-13 exchange)
- exec does NOT change the pid. The chain is one pid, one pgid, one ps start time, one command line, first step to epitaph — externally indistinguishable from a while-loop process. Fork happens once, at chain start. Kill and stop work unchanged (stop discovers by lock fd anyway, §2.9).
- The image reload is not overhead to apologize for; it is an extremely strict state-safety mechanism. The only observable difference from an in-process loop is whether RAM can smuggle state across a step boundary. exec makes per-step statelessness STRUCTURAL — nothing can survive — where a loop makes it disciplinary (reviewable, driftable: cached context, held-open writers, parsed config accreting).
- Consequence: the crash-recovery path and the normal path are one code path, exercised at every step boundary forever. Cold entry never becomes a mode. Same move as §2.3 "replay stops being a mode" — the family resemblance is the point; name it.
- The disk re-derivation is paid in BOTH models (§6 position derivability), so the true delta is a page-cache-warm image load: single-digit ms against a model call.
- The escape hatch is already sanctioned and severable: §3.4 permits in-process re-entry through the CLI dispatcher as a per-procedure implementation detail. If measurement ever cares, that optimization changes zero interface and zero spec. Choosing exec costs nothing to reverse; choosing in-process deletes the structural guarantee.
- Single-step operation ("advance one step" vs "run to epitaph") is one verb + a continuation decision from disk; an operator flag lands when a concrete operation asks, not preemptively.
