## The defect

`lernie new` snapshots the **whole** data-root pool into the config commit's
`descriptions/**` (ARCH §3.3 *Descriptions-always population*), and the dispatch
commit (§2.3 step 2) strips the control files but deliberately leaves
`descriptions/**` in place. So every agent branch carries schemas and skill
blurbs for all five shipped tools regardless of what its role's `tools:` grants.

The wire array, by contrast, is the intersection of the grant with the snapshot
(`src/prompt/dispatch/tools.rs::compose`). The agent therefore has strictly more
filesystem visibility than capability, and nothing on its branch distinguishes
the two: `providers.yaml` — the actual grant — is removed from the agent's tree
by the dispatch commit and lives only on `config/*`.

Observed cost, twice: asked "why can't you send a message?", the agent
`bash`-explored `descriptions/`, found `descriptions/tools/message.json` plus
`descriptions/skills/message.md`, concluded (messages/010) *"this environment
seems to support messaging"*, and only after ~8 more steps landed on the true
answer (messages/018): *"only bash, read_file, and load_skill are actually
exposed to me as callable tools here."*

## It also breaks a stated invariant

ARCH §5.1: *"Everything inside a branch's worktree is composed into that agent's
prompt. There is no exclusion list, no filter, no 'this path is for the harness
only.'"*

A non-granted tool's descriptors compose **nowhere**: `assembler/body.rs` skips
`descriptions/tools/**` and every tool-claimed skill description (`tool_backed`,
per §3.3's *two wire homes*), and the tools array does not carry them because
the role did not declare them. They are worktree content with no wire home —
exactly the exclusion §5.1 says does not exist — reachable only by `bash`.

## Deliverable

Make what an agent can **see** equal what it can **call**, with no new artifact:
extend the dispatch commit's existing tree-trim so it prunes
`descriptions/tools/<name>.json` (and the tool-claimed
`descriptions/skills/<name>.md` beside it) for every tool the forking role does
not grant. Standalone skills — those no tool claims — stay: they compose as head
text and are `load_skill`-able.

One predicate, at the one place the tree is already trimmed
(`step_commit::remove_control_files`, called by both the root dispatch commit and
`subagent::spawn_subagent_branch`). No second source of truth for the grant, so
nothing can drift from it. `ls descriptions/tools/` becomes the one-step answer
to "what can I call?".

Rejected alternative: committing a resolved-grant file (`role.json`) into the
worktree. It leaves the misleading descriptors in place and creates a second
representation of one fact — the drift PRINCIPLES bans.

Known consequence, spec-sanctioned: a compactor (`tools:` empty) loses the
verbatim schemas its inherited transcript names, so §3.3's closure stands in a
bare `{"type":"object"}` — *"the entry exists to make the history legible, not
to offer the tool."* `src/e2e/compaction_wire.rs` asserts the name is declared,
not the schema body.
