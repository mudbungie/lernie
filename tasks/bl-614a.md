Measured 2026-09-06. yog published v0.0.53 at PROTOCOL 18, carrying the root
`PROTOCOL` file. lernie's release pull request (v0.1.50) stood open and CLEAN —
every guard would now pass, the protocol gate included. A `workflow_dispatch`
of Release-plz SKIPPED the `merge the release PR` job, so nothing merged it.

WHY. The job carries `needs: prune-release-branches`, and prune carries
`needs: release-plz-pr`, which is push-only
(`github.event_name == 'push'`). A bare `needs` carries an implicit
`success()`, so a SKIPPED dependency skips the job — on a dispatch the whole
chain skips. The file states that as a feature in two places: the merging
step's terminator comment ("that dispatched run does not reach this job at all
— `release-plz-pr` is push-only, so it, `prune` and this job are all skipped on
a dispatch") and the dispatch step's own comment ("the run is exactly `ci` +
`release` + `macos`").

That is right about the POST-MERGE dispatch, where re-entry buys nothing, and
wrong about the case that actually happens. Guard 3 — the protocol gate — is
the only guard whose answer changes with nothing in this repository changing:
it clears when the ENGINE publishes, an event this repository never sees. The
job's own hold message already promises the door — "a later push to main, or a
re-run of this workflow, re-judges" — and a re-run cannot re-judge while the
re-run skips the job. A held release therefore waits for an unrelated landing
on `main`.

yog's `release-automerge.yml` has the door and names it in the comment it
leaves on a held pull request: a `workflow_dispatch` of that workflow "is the
door when the fix landed elsewhere."

THE FIX. The merge job runs on `workflow_dispatch` too, re-judging the open
release pull request against the newest published yog tag. `needs:` keeps the
ordering it was written for — behind the PR job and the pruner, so prune's "has
no open PR" test still reads the state it was written against — and the gate
moves into an explicit `if` that admits `prune-release-branches` being
`skipped`, which is exactly what a dispatch does to it. A FAILED pruner still
skips this job, and the owner guard, which used to arrive through the chain, is
restated here because an explicit `if` no longer inherits it. The two stale
comments are corrected in the same edit: the recursion stop is that a
dispatched run refreshes no pull request and finds no candidate, not that the
job is unreachable.
