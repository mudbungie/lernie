A running agent is welded to the config it forked off, for life, with no verb to move it. `retarget` is the way out.

## The trap (observed in yog, conversation `ladies`, 2026-08-07)

An agent's model failed on an expired credential. The operator changed the model. The change landed correctly on `config/default` (`a06b090`) and governed nothing: the agent forked `d93c2a9` two days earlier, and §2.2 derives control from ancestry — "the nearest ancestor of the agent's branch reachable from any `config/*` ref. Derived from ancestry, never stored." The reprompt dispatched the same model and failed identically.

Forking does not escape it. `src/prompt/fork_point.rs:16-18`: "the governing config commit is derived from that ancestry like any other agent's, so **fork is the freeze** whatever the fork point is." A fork off an `agents/*` commit still merge-bases to `d93c2a9`. The operator's only alternative is to abandon a live conversation's whole history to change a model id — and that is exactly what yog's one exit offers today ("start a new conversation").

## Design, refined against the tree (Ptarmigan, 2026-08-07)

**Not a merge.** §2.3's invariant is unconditional: *"an agent branch advances only by its executor (§2.11). No branch has a second writer, and nothing merges into either kind."* The obvious precedent — compaction's `--no-ff` merge — was **retired** by bl-bc9c; §2.6 records the result as "leaving no merge anywhere in the system." A retarget merge would reintroduce precisely what was removed.

**Retarget is a re-fork, and it is the compaction landing's own two moves.** `compactor::land` (`src/prompt/compactor/land.rs:103`) mints a base commit, then replays the tail onto it with `git rebase --empty=keep --onto <base> <point> <branch>` (`land/replay.rs`). Retarget is the same shape with a different base:

1. **The base is a re-derived dispatch commit.** Not the old one rebased — a *newly minted* one on top of the target config commit, through the fork's own machinery (`dispatch/step_commit/descriptors.rs`, the `Grant` triple). This is the move that makes the whole thing fall out:
   - The §3.3 descriptor cut is **re-derived, never replayed** — which §3.3 already requires ("The derivation reads that commit and never the tree it forked off"). Minting a dispatch commit *is* that derivation, so nothing special is written for it.
   - The control-file removal (§2.2, "enforced by removal rather than by trusting nobody looks") is re-performed against the new config, so the modify/delete conflict a naive rebase would hit on `providers.yaml` — the new base modifies it, the old dispatch commit deletes it — never arises. The base already has it gone.
   - `goal.md`, `soul.md`, `name` are re-pinned from the same sources the original fork used.
2. **The replay** is the agent's post-dispatch commits: `git rebase --empty=keep --onto <new-dispatch> <old-dispatch> agents/<id>`. Transcript entries are one immutable file each with monotonic names (§2.3), so this is conflict-free by the same construction compaction relies on, and the same stage-reading decline applies where it is violated (`refs/lernie/conflicted/<agent-id>`, branch restored bit-for-bit by `rebase --abort`).

After it, `governing_config` — unchanged, still a pure ancestry query — answers the target commit. No new stored fact anywhere.

**The user act is a ref mark, so the single-writer rule is untouched.** `lernie retarget <workspace> <agent-id> [--config <name>]` writes `refs/lernie/retarget/<agent-id>` at the target config commit; the agent's **own executor** consumes it and lands it at the next `advance` step boundary, exactly where `compactor::land` runs. Ref marks as orthogonal, non-derivable state are the established pattern (§6: `mark_abandoned`, `notify_ui`; §2.6: `budget-exhausted`, `conflicted`).

**The legitimacy argument is §2.6's own.** *"Why this one rewrite is legitimate where merge-back was not is the two-channels polarity — a compactor's payload is the dispatching branch's own context, rewritten on purpose — its payload, not its contamination."* A retarget's payload is the branch's own **policy**, re-forked on purpose. Same polarity, same landing, same writer.

**Timing is semantics, not compromise.** The mark takes effect at the agent's next step, never mid-step. A config governs steps; the retarget is in practice followed by a reprompt, which *is* that next step.

## Pre-flights (before any mark is written, leaving no debris)

- The agent id guard every id-taking verb shares (§2.11 deposit rule).
- The target resolves to a `config/*` commit; a target already governing the agent is a clean no-op, not an error.
- `Error::GrantUndescribed` — the role's grant must be described by the target config (§3.3's validity-before-fork discipline, pre-flighted in the parent's worktree exactly as `child_dispatch::run` does).

## Deliverable

- `lernie retarget` (§3.4 verb, one-product convention) + the mark.
- The landing at the `advance` step boundary, consuming the mark: re-forked base, then replay.
- ARCHITECTURE §2.2 *Fork is the freeze* amended — the exit named where the freeze is stated, since that paragraph today reads as though there is none; §2.3's invariant restated unchanged and shown to hold (the executor is still the only writer); §3.4's verb list; §11 unchanged (this is not the deferred "live config update" — the freeze still holds by default, and what is added is a deliberate, auditable break of it).
