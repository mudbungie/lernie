Release PR #7 (`chore: release v0.0.7`) is open. Per the `promote-changelog` target's header and `release-plz.yml`'s, the accumulated `## [Unreleased]` section must be stamped as `## [0.0.7]` and merged to `main` **before** that PR merges, so the tagged tree's changelog is already correct.

Two moves, one commit, because the second is caused by the first.

## 1. Promote

`make promote-changelog VERSION=0.0.7` — stamps `[Unreleased]` as `[0.0.7]` with its compare link and date, and opens a fresh empty `[Unreleased]` above it. It refuses a version the file already carries, so a re-run is a no-op failure rather than a duplicate section.

## 2. Exempt release-prep commits from the changelog guard

`tests/changelog_completeness.rs` (bl-d92b) asserts that every `[bl-xxxx]` id on `main` since the last `v*` tag appears in `CHANGELOG.md`. **This ball's own commit would fail it**: a release-prep commit carries a ball id but is process rather than product — it lists no delivery, and a bullet describing "the changelog was promoted" is noise in the release notes it is promoting. The precedent is on `main` already: `0ff056a`, *"0.0.6 release prep: promote the changelog [Unreleased] section to [0.0.6] [bl-7cff]"*, has no bullet and was one of the ids the guard flagged when first run over the full history.

So `delivery_id` gains one exemption beside the gate-close one, keyed on the `release prep:` subject convention the `promote-changelog` target establishes, with the classifier test extended to pin it. Both exemptions are the same rule — *process, not product* — which is the wording `CHANGELOG.md`'s own header uses for gate closes.

The exemption must land in the **same commit** as the promotion (or before it); shipping the promotion alone leaves the next close red.

## Gate

`make check` green on the merged tree, including the guard passing over a `main` that now carries this very commit.
