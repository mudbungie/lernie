The dispatch built-in tool runs during the parent's tool step: the child forks off the parent tip, which at that instant ends with the assistant tool_use transcript entry — the answering messages/NNN-tool.json commits only after the tool returns. The child therefore inherits a transcript whose last entry is an unanswered tool_use, and its first model call is refused, e.g. {"type":"error","kind":{"provider":{"status":400}},"message":"No tool output found for function call call_…"}. Minimal repro: lernie prompt <ws> 'dispatch a worker with goal X', then read steps/<child>/001/response.json. Live evidence: /tmp/claude-1000/-home-mark-dev-lernie/d8b3c251-6d27-458f-a55c-166907ca93db/scratchpad/fleet-e2e/run-20260730-170616-2049225/ws/steps/*/001/response.json (child has inherited messages/004-gpt-5.4.json tool_use, no 005-tool.json; parent's 005-tool.json holds the matching tool_use_id). The lernie dispatch CLI path is clean (no pending tool_use at a step boundary). This kills the entire agent-initiated dispatch path end-to-end, and the parent only ever learns 'a child returned' (died/error epitaph). Fix candidates, coordinate with ARCH §2.5/§2.3: (a) the child's dispatch commit deletes the inherited trailing unanswered tool_use entry (transcript change is append-or-delete, §2.3); (b) assembly skips a trailing unpaired tool_use; (c) fork the child off the settled step instead. Pick one, spec it, test it against a mocked wire.
