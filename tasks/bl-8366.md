Systemic hazard seen during parallel development: the gate's e2e tests exec whatever `bz` is on PATH (~/.cargo/bin/bz, machine-global mutable state); any agent's `make install` / `make test-install` rewrites it at THEIR tree's pin, and another worktree's gate then fails five-plus e2e tests on the load-time version guard (ARCH §4.4) — indistinguishable at a glance from a code regression.

## Decision: the Makefile, not the Rust fixtures

Both candidates were live (ball body + brief). Chose the **make prerequisite**:

- **Single source, no duplication.** The pin already has exactly one derivation per side: `BRAZEN_PIN` in the Makefile (Cargo.toml's `brazen = \"=\"` line) and `brazen_pin()` in the crate. The Makefile is the one place that knows BOTH the pin and how the tests are launched, so wiring PATH there adds no new derivation. A Rust fixture would have had to duplicate the `cargo install brazen --version =<pin>` recipe that already lives in `install-bz`.
- **Every spawn site, for free.** 30+ sites across `src/e2e/`, `src/prompt/**/tests`, `src/template/tests_*`, and `tests/*.rs` spawn the binary; PATH is inherited, so one prepend covers all of them and every future one. A fixture would have needed each site funneled through a new constructor — and `tests/*.rs` cannot even reach `crate::test_support`.
- **No coverage cost.** A Rust installer's cold-install branch never executes on a warm run, so it would have to be excluded from the 100% floor or hidden under `src/e2e/*`.

Accepted gap: bare `cargo test` still inherits the ambient `bz` (documented in the README, with `make install-bz` as the cure).

## Mechanism

    XDG_CACHE_HOME ?= $(HOME)/.cache
    BZ_TEST_ROOT   := $(XDG_CACHE_HOME)/lernie/bz/$(BRAZEN_PIN)
    BZ_TEST_PATH   := $(BZ_TEST_ROOT)/bin:$(PATH)

`test` and `coverage` take `\$(BZ_TEST_ROOT)/bin/bz` as a file prerequisite and run under `PATH=\"\$(BZ_TEST_PATH)\"`. The directory is NAMED after the pin, so a bump is a cache miss and nothing else and no entry is ever overwritten in place — what makes the cache safe to share across parallel worktrees. Cold: one `cargo install` (~25s measured) per pin per machine. Warm: a stat.

Verified on this worktree with pin 0.0.3 against an ambient `bz` 0.0.4: bare `cargo test` fails the same five e2e tests every run; `make test` passes all of them.

## Landed

- Makefile: `BZ_TEST_ROOT`/`BZ_TEST_PATH` + the file target; `test`/`coverage` depend on it; `install-bz` and `test-install` comments corrected (neither is a test prerequisite any more).
- `src/prompt/tests/pin.rs`: `the_makefile_derives_the_same_pin` — `make brazen-pin` must equal `brazen_pin()`, or the tests would fail the guard against a binary the Makefile itself installed.
- `.github/workflows/ci.yml`: dropped the now-redundant `make install-bz` step; one pin-keyed cache entry covering both adapter homes (`~/.cache/lernie/bz`, `~/.cargo/bin/bz`), both populated by `make ci` itself.
- README: new contributor section "The pinned adapter under test" (the trap, the cure, the two consequences), plus the CI paragraph and the build-target table rows.

Runtime resolution for real use is untouched (§4.4 order: `adapter:` override, injected target, else `bz` on PATH); `make install` still puts the pinned `bz` on the user's PATH.
