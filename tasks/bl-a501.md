## Operator ask (2026-08-01, filed from yog operation)

Agents should have a tool to `cd` — change their own working directory. Today an agent is nailed to one cwd for its whole life and must prefix every bash command with `cd X &&`.

## Verified code facts (verify again before editing — do not trust this ball blindly)

- `src/prompt/tool/builtin/bash/mod.rs` header: 'The shell inherits this process's working directory, which the executor pinned to the calling agent's worktree before spawning `lernie tool bash` (§3.3 Working directory). That inheritance is the whole mechanism: the cwd is resolved once, where the tool call's identity is known.'
- `src/prompt/tool/subprocess.rs`: every child spawns with an explicit `SpawnArgs::cwd`.
- Builtins live in `src/prompt/tool/builtin/` (bash, read_file, load_skill, message, dispatch, compaction).

## The design question (settle it in ARCH before coding)

'cwd resolved once' is doctrine (ARCH §3.3). A cd tool makes cwd a **mutable per-agent fact**: default = the agent's worktree (today's behavior, unchanged when the tool is never called), mutated by an explicit `cd` tool call, consulted by the executor at every subsequent spawn. Single source of truth: one stored cwd fact per agent, everything else derives. Where does that fact persist so it survives across turns/process boundaries? Follow how other per-agent state already persists — do not invent a second mechanism. Amend ARCH §3.3 and the bash builtin's header doc as part of the change; a silent deviation from the doc is a bug.

Semantics to pin: `cd` takes a path (relative resolves against current cwd); refuse a nonexistent directory with a clear tool error; result reports the new absolute cwd. Consider whether escaping the worktree should be refused or allowed — look for an existing containment doctrine in ARCH first, and follow it rather than inventing policy.
