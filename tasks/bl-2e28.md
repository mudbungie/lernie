Reasoning: an integration is an external binary (PRINCIPLES "Integrations are external binaries") so it must NOT be a lernie verb; and "if it can't be tested, it mustn't be built" rules out a scripts/ shell script outside the coverage gate. The crate rides the workspace gate and is exercised against a stub `lernie` (crates/lernie-eval-agent/tests/driver.rs, 9 tests) — same no-live-traffic discipline as the runner. It drives the harness exclusively through the front door, exec'ing `lernie` from PATH (`new` → `config` → `prompt`); no linked binding — tool subprocesses need an exec'able lernie anyway, so linking buys nothing. `--agent` stays REQUIRED, no default: the driver is an experiment-defining input.

Per run: (1) seed the run's isolated LERNIE_HOME from the machine's lernie config root ($XDG_CONFIG_HOME/lernie else ~/.config/lernie; LERNIE_HOME deliberately ignored — it names the per-run home) — models.yaml + template/ override, seed-if-absent; the wire is machine-local by design (§4.2/§9.2) and these are the two existing front doors, so no new flag/env exists; (2) `lernie new`; (3) APPLY the experiment (END 2): `lernie config <ws>` with EDITOR='cp -f "$LERNIE_EXPERIMENT"' — the experiment lands as an ordinary config commit, the only place the harness reads workflow policy (§2.2); baseline's empty diff declines cleanly; (4) `lernie prompt` with the task prompt grounded in the shared cwd; (5) write LERNIE_EVAL_REPORT (workspace, agent id).
