THE ACT. The operator has greenlit the coordinated cutover (yog REMOTE §12): the
seat's first release under this name, at 0.1.0. This is the moment the name
`lernie` publicly changes meaning — through 0.0.x it was the agent-loop engine,
which continues as `litany`; from 0.1.0 it is the seat. The version is the only
rule separating the two eras in the published record, and it cannot be corrected
in place, so the README that ships IS the disambiguation.

WHAT THIS BALL DOES.

1. Run the AGENTS.md *Before the first publish* checklist in full — all seven
   items — and record each verdict here. It is a person's checklist rather than
   a gate on purpose: every item is a one-time judgement whose remedy is
   destructive, so a green checkbox would be a worse answer than looking.
2. Audit the real `cargo package --list` against what the guard promises. The
   guard judges file CLASSES and never content; auditing the content of the
   list is the half only a person can do.
3. Flip `publish = false` to publishable, with the manifest comment rewritten
   to say what actually holds now. THE FENCE STATEMENT STAYS — the version rule
   outlives the flag, and it is the thing a later editor most needs to read.
4. `cargo publish --locked`, then verify the registry serves 0.1.0 and that its
   rendered page carries the fence-stating README.

WHAT THIS BALL IS NOT. It is not a release workflow. There is deliberately no
`make publish` and no automation for this act; a convenience target for an
irreversible act is how the act happens by accident. The recurring release path
is filed separately.

## The checklist, run in full — verdicts

AGENTS.md *Before a publish*, all seven items. Each was measured, not assumed.

**1. History — CLEAN.** Every commit reachable on the trunk was handed to
`leak-scan.sh --commit`, which reads the blobs that commit adds or rewrites
plus its message. The union of those sets is every blob the trunk has ever
carried, so this is a whole-history sweep rather than a tip scan. Sixteen
commits, no disclosure findings on any. The tree was gated from its founding,
which is why this was cheap rather than unnecessary.

**2. Other refs — CLEAN, and the one probe is already gone.** No tags. The one
probe branch this repository ever had was pushed to buy a runner verdict on the
CI workflow and was deleted with its pull request, as the discipline requires;
the remote now serves the trunk, the task store, and the pull ref GitHub keeps
forever. That pull ref's commit was scanned on its own and is clean. The task
store's published tip was cloned fresh from the remote and scanned by this
repository's own rule table: clean. There is no landing ref on this remote.

**3. Commit messages — CLEAN.** Covered by item 1: the commit scope reads the
message, and every message on the trunk was read. The probe's message too.

**4. Repository text nobody committed — FINDING, and the remedy is not a
scrub.** No issues, no releases. One pull request, and its body carries an
agent-session URL — a conversation id, which is the last class on the
never-publish list and is no more publishable in a pull request than in a ball
body. Two things follow. Editing the body does not remove it: GitHub keeps a
body's edit history and serves the pull ref forever, so an edit buys the false
assurance a history rewrite buys elsewhere — the same reasoning that made a
squashed initial commit the right remedy upstream rather than a filter. And the
scanner did not catch it, which IS fixable: the `session-artifact` rule's
prefix alternation does not name this form. Filed as bl-9fbe, with the fixture
line that closes it and the note that the same hole is in the upstream copy of
the table. The registry description and metadata were read and are clean.

**5. Actions logs and artifacts — CLEAN.** Six runs, every one green. A failed
gate is what prints paths into a public log, and there has not been one. No
artifacts uploaded.

**6. Already-published versions — NONE from this tree, and this is what stopped
the publish.** Nothing has been published from here, so items 1 and 2 still have
no deadline. But the NAME is not new: the registry crate carries the engine
era's twelve 0.0.x releases and is configured to accept **Trusted Publishing
only**, so `cargo publish --locked` was answered `403 Forbidden` — with the
package built, verified and uploaded, and refused at the registry. Nothing was
published. `publish = true` is necessary and not sufficient; the switch is
registry-side and no manifest edit can satisfy it. See the act's verdict below.

**7. The fence — INTACT.** The version is 0.1.0, on the seat's side. The suite
asserts it two ways: one test parses the crate version and fails any 0.0.x, and
another requires the usage text to state both eras and to name the engine's new
name. Both green.

## The packaged list, audited by content

`cargo package --list` answers **122 paths: 116 under `src/`, plus `Cargo.toml`,
`Cargo.lock`, `README.md` and `LICENSE`** — exactly the four tree roots the
allowlist rules in — and the two files cargo mints into the tarball itself
(`Cargo.toml.orig`, `.cargo_vcs_info.json`), which are not tree files at all.
Nothing else. The guard test judges file CLASSES and never content, so the
content half was done by hand: no `docs/`, no `tests/`, no `scripts/` — the
fabricated-secret fixtures among them — no `corpus/`, no `rules/`, no workflow
or hook, no agent guide, and no `assets/`. The disclosure gate over the same
tree is clean, and item 1 says the same of every version of every one of those
files that ever existed. With no allowlist at all this crate would package 298
files.

## The act — REFUSED at the registry, and nothing was published

```
error: failed to publish lernie v0.1.0 to registry at https://crates.io
Caused by:
  the remote server responded with an error (status 403 Forbidden): New
  versions of this crate can only be published using Trusted Publishing
```

The crate's public record states it without authentication: `trustpub_only` is
true. A trusted publisher is already registered on it from the engine era, and
it names provider, repository and workflow FILENAME, all matched literally
against the OIDC claim. The repository half still matches — the engine's
repository was renamed and this one took the name — so the publisher does not
need registering; it needs a workflow file at that exact name.

**Two owner acts open the path, and neither is a code change here:**

- **Relax the registry setting** for this crate and re-run `cargo publish
  --locked` from a checkout at this tree. This is the route the greenlight
  assumed, it is minutes, and it is the faster way to fix the fence in the
  public record.
- **Land the release workflow** (bl-459d) at the filename the existing trusted
  publisher already names, and let the first release be the pipeline's. Slower,
  and it makes the first release under the new name also the first exercise of
  an untested pipeline — which is an argument against, not for.

**What this ball leaves behind, all of it landed:** the flag flipped with the
manifest comment rewritten to state that it is necessary and not sufficient and
why; the fence statement above it untouched; AGENTS.md's section retitled
*Before a publish* — it is not a one-time rite — with items 4 and 6 carrying
what they found; DESIGN §6 rewritten, and a stale cite in `store-scan.yml`
corrected on the way past. The tree is ready to publish the moment either owner
act is taken; nothing further is needed from it.
