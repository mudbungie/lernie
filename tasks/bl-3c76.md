Source: coding-harness comparison survey 2026-08-01. Verify every premise against current source before ruling.

## Verified seam, unresolved architecture

Lernie can expose external `lernie-tool-<name>` binaries with static schema/skill descriptors. No suite component currently speaks MCP. An MCP bridge could open useful integrations, but a long-lived MCP server has dynamic tool discovery, session lifetime, transport, credentials and capability questions that a one-process-per-tool-call adapter does not answer. Breadth alone is not a P0 coding-quality gap.

## Deliverable: tracked design, not core implementation

Settle the smallest external integration before filing code:

1. Placement outside lernie core: in-repo integration binary vs sibling/deployment component, applying PRINCIPLES "Integrations are external binaries."
2. How dynamic MCP tool descriptors become a deterministic, cache-stable lernie tool pool without a duplicate registry.
3. Server/session lifetime across separate tool invocations; startup, reconnect, cancellation and failure semantics.
4. Stdio transport first; HTTP/OAuth only after a named deployment requires them.
5. Credential ownership and redaction.
6. Capability metadata and enforcement, waiting on the yog capability-boundary ruling (yog bl-0cea); no bridge that bypasses policy.
7. Lazy discovery/token cost and a concrete Slack-or-equivalent acceptance story.

Refuse MCP in lernie core, a marketplace, and multiple transports before one deployment proves the seam. The design may conclude that a deployment-owned bridge is enough and close with no lernie product code.
