Found while landing bl-8366. Under a plain `cargo test --lib` (default parallelism, loaded box) these two fail intermittently — 2 of 3 consecutive runs:

- `cmd::tests::verbs::config_reports_a_declined_pass_as_a_clean_line` (src/cmd/tests/verbs.rs:151 — the second pass returned something other than `Outcome::Line`, i.e. it was NOT declined: something changed between the two no-op editor passes)
- `cmd::tests::verbs::config_authors_a_commit` (src/cmd/tests/verbs.rs:131)

Both pass in isolation and both pass under the gate, because tarpaulin.toml pins `--test-threads=1`. So the gate never sees it and it is not a delivery blocker — but it makes bare `cargo test` an unreliable signal for anyone iterating, which is how it was found.

NOT the bz/PATH class of failure (bl-8366): reproduced with the ambient and the pinned adapter alike, and these tests never exec `bz`. Sibling flakes: bl-2061, bl-9300 (spawn_retries_past_transient_etxtbsy).

--- RESOLVED (Tiller) ---

CONFIRMED MECHANISM: `config::run` calls `harness_root::resolve()` (src/harness_root.rs) directly and unmocked, which reads the process-global `LERNIE_HOME` env var. `config_authors_a_commit` and `config_reports_a_declined_pass_as_a_clean_line` read this ambient value with no isolation at all, so `roots.data` resolved to whatever the process's real environment was at that instant — on a dev box, the real `~/.local/share/lernie` pool.

The crate already had one guarded mutator of this process-global var: `with_lernie_home` in `src/cmd/tests/mod.rs`, serialized by a `Mutex` (`ENV_LOCK`), used by `new`/`prime` tests. But (a) the two `config_*` tests never went through it, so their reads raced the ambient value against every other test's `with_lernie_home` window, and (b) a *second*, entirely unguarded mutator existed: `src/e2e/bundle_replay_cli.rs::replay_cli_lands_under_lernie_home` called `std::env::set_var`/`remove_var` directly, justified only by a stale comment ("SAFETY: single-threaded test run (tarpaulin.toml --test-threads=1)") — true for the gate, false for bare `cargo test --lib`.

Proved with instrumentation (eprintln'd thread id + `LERNIE_HOME` value at each `harness_root::resolve()` and `commit_checkout` call, later stripped): wrapping only the two `config_*` tests in `with_lernie_home` was NOT sufficient — `config_reports_a_declined_pass_as_a_clean_line`'s second pass still observed `LERNIE_HOME=None` mid-closure (lock held) because `bundle_replay_cli.rs`'s unguarded `remove_var` fired concurrently, outside `ENV_LOCK` entirely, yanking the var out from under the guarded window. The pool that then leaked in on the "declined" pass matched byte-for-byte the real ambient pool (`~/.local/share/lernie/{tools,skills}`: bash, dispatch, load_skill, message, read_file) — direct confirmation of the ambient-env-leak theory in the original ball body, not the "§3.3 refresh is order-sensitive" alternative.

FIX (test-side only, no production change): consolidated both mutators onto one shared, lock-guarded helper.
- Moved `ENV_LOCK` + `with_lernie_home` out of `src/cmd/tests/mod.rs` into `src/test_support.rs` (already the crate's shared in-process test-helper module, `#[cfg(test)]`, used by both `cmd::tests` and `e2e`), made `pub`.
- `src/cmd/tests/verbs.rs`: `config_authors_a_commit` and `config_reports_a_declined_pass_as_a_clean_line` now wrap their `config::run` call(s) in `with_lernie_home(scratch_dir, ...)` — the declined-pass test wraps *both* passes in one call so they share one lock-held window and see an identical (empty) data root.
- `src/e2e/bundle_replay_cli.rs::replay_cli_lands_under_lernie_home`: replaced the raw `set_var`/`remove_var` pair with `crate::test_support::with_lernie_home`.

No production code touched (`harness_root.rs`, `config.rs`, `template/*` all unchanged) — this was purely a test-isolation gap, not a behavior bug.

DETERMINISM EVIDENCE: 44 consecutive `cargo test --lib` runs (default parallelism, on a box already under load average 30-50 from concurrent sibling drives) — 0 failures across `config_authors_a_commit`, `config_reports_a_declined_pass_as_a_clean_line`, and `replay_cli_lands_under_lernie_home` (previously silently relying on serial execution too, now fixed as the same bug's second instance).

SCOPE NOTE for bl-6987 (Keelson, wall-clock-assumption sweep): this class — "a helper's own doc comment justifies an unguarded env/global mutation by citing `--test-threads=1`, true only under the gate" — is worth grepping for elsewhere (`rg 'test-threads=1' -g'*.rs'` / `rg 'SAFETY: single-threaded'`) since `bundle_replay_cli.rs` had exactly one such instance sitting undetected next to the one that *was* guarded.

Gate: `make check` green (fmt-check, clippy -D warnings, 100% coverage via tarpaulin --test-threads=1, install contract).
