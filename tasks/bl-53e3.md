BLOCKS THE 0.0.1 RELEASE (bl-9253). Ops agent Halyard hit this 2026-07-26; ops-only, so filing rather than fixing.

SYMPTOM
CI on main went GREEN first pass (run 30216420512, commit 39c10a5) — the bz-install fix from bl-636b/bl-8366 works. Release-plz then fired via workflow_run (run 30216800926) and the 'release-plz release' job FAILED in 23s at the 'Run release-plz' step, before any publish, tag, or GitHub Release:

    INFO using release-plz config file release-plz.toml
    ERROR Package `agent-eval` has `publish = false` or `publish = []` in the Cargo.toml, but it has `publish = true` in the release-plz configuration.
    Error: Package `agent-eval` has `publish = false` or `publish = []` in the Cargo.toml, but it has `publish = true` in the release-plz configuration.
    ##[error]Process completed with exit code 1.

This is a hard abort of the whole release command — lernie is not published either. crates.io still shows only 0.0.0; origin has NO tags at all; no GitHub Releases exist.

ROOT CAUSE
crates/agent-eval/Cargo.toml carries `publish = false` (landed with a936923 [bl-8801], 'resolve the eval island').
release-plz.toml declares agent-eval's exclusion with ONLY:

    [[package]]
    name = "agent-eval"
    release = false

release-plz's per-package `publish` key defaults to TRUE and is validated INDEPENDENTLY of `release`. `release = false` does not imply `publish = false` to the validator, so the two files disagree and release-plz refuses to run rather than releasing anything.

Why it was not caught earlier: the 'release-plz PR' job (run 30216420496) SUCCEEDS — release-pr does not run this consistency check. Only `release-plz release` does. The release job had never reached this point before, because the previous attempt's CI was red (see bl-9253 history).

FIX (one line, config only)
Add `publish = false` to the existing agent-eval block in release-plz.toml:

    [[package]]
    name = "agent-eval"
    release = false
    publish = false

Keep/extend the comment above it to say WHY both keys are needed — that `release = false` alone does not satisfy release-plz's publish-consistency validation against Cargo.toml's `publish = false`. Single source of truth caveat worth noting in the comment: Cargo.toml stays authoritative on publishability; the release-plz key exists only to agree with it.

VERIFY BEFORE MERGE
Locally: `release-plz release --dry-run` (or at minimum confirm release-plz parses the config without the consistency error). Do not hand-edit anything else in release-plz.toml.

AFTER MERGE
Halyard (or whoever holds bl-9253) pushes main; green CI then re-fires release-plz and 0.0.1 should publish via trusted publishing (OIDC — no CARGO_REGISTRY_TOKEN; `gh secret list` is correctly empty). NEVER rename .github/workflows/release-plz.yml — crates.io trusted publishing is bound to that exact filename.
