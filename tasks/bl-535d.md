## Direction (user-set)
Enforced death via kernel pgid semantics across agent boundaries is wrong for the non-hierarchical parent/child model. Cascade becomes a CLI-level walk, opt-in via `lernie stop --stop-children`.

## Refinement
Walk the agent **id namespace**, not tool invocations: descent is already encoded in the hyphenated agent id (§2.3), so children of X are exactly the branches/inboxes prefixed X- (single source of truth; a tool-invocation walk would re-derive what the namespace states). The flag enumerates the prefix and issues `lernie stop` per child found, recursively.

Kernel pgid semantics REMAIN for one executor's own subprocesses (bz, tool processes — §2.9 steps 1-2): those are the executor's limbs, not agents, and must die with it (in-flight HTTP dropped). Only the agent→agent cascade moves to the CLI walk. Consequence: dispatch's no-setpgid-for-child-harnesses rule (§2.9) is retired — child executors take their own pgid like roots do; a deposit-launched driver likewise (setsid at launch), which dissolves the revival-driver collateral-kill hazard.

## Semantics to pin while editing docs
Default (no flag) = stop the one agent only. This flips ARCH §2.5 ('a child must reach a terminal state before its parent terminates — parent termination cascades a stop') and PRINCIPLES 'Stops are aggressive and cascading' — amend both, don't deviate silently. Note the coherent consequence: an orphaned child later deposits its result into the stopped parent's inbox, and the deposit revives the parent (§2.11) — stopping a parent no longer strands its children's returns.
