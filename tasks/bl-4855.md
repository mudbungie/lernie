bl-5c53 landed the read half: the lineage listing, the five destinations as one
typed `Where`, and a pane that paints a config file's bytes beside the settings
the engine's schema found in them (DESIGN §4.29). What it did not build is the
write, and the reason is a hazard rather than time.

## The write is one field, and the field is not the problem

`config` is one op that is a read or a write depending on whether it carries
`text` at all (upstream's own discriminator, REMOTE §8.5). So the act is the
read's envelope plus the whole new text:

    {"op": "config", "target": <the same target the read carries>, "text": "…"}
      -> a file destination answers the path written; a lineage answers
         `litany config`'s captured run (`reply/outcome`, already painted)

## The hazard: three of the five destinations name no workspace

`litany-models`, `litany-workflow` and `cadence` are the ENGINE's own files and
carry no workspace anywhere in the envelope. This seat's poster fans every
gesture that names no workspace — `crate::offframe::poster`, bl-40ec — so an
ACT composed for one engine's `cadence.yaml` would be sent down **every channel
this box holds**, writing the operator's text onto every engine they are a
client of. The read half dodges it by not posting at all: a standing read is
asked down the aimed channel by name.

Three shapes to attack before writing a line of it, and the ball should record
which was taken and why:

- **Post through a channel-addressed door.** The poster's split is
  `workspace present → route, absent → fan`; a third arm — *this act names a
  channel* — is a new mechanism on the one queue REMOTE §3's *sent exactly once*
  rides on.
- **Refuse to write the engine's globals from a seat**, and offer the editor
  only for the two destinations that name a workspace. Subtraction, and it costs
  the operator the two files they most want to edit.
- **Carry the aimed workspace in the target anyway.** Upstream's `decode_file`
  ignores unknown keys, so it would route correctly and be ignored on arrival —
  and it is the seat asserting a thing about a file that is not true of it.

## The other three questions the write raises

- **Is it destructive?** It replaces a file's whole bytes and a lineage write is
  a commit. DESIGN §4.20's idiom (an arming that is an enablement, and an
  unmaking that is a place) exists for acts that cannot be undone by doing the
  other thing; a config write can be undone by writing the old bytes back, which
  the pane is holding. Decide whether that makes it ordinary, and say so.
- **The editor needs a box**, and `crate::ui::keys::BOXES` is the whole list of
  boxes that take text — a fourth joins it in the commit that paints it.
- **`litany-workflow` has no read either**, because it is addressed by a name
  and nothing lists what names exist. It arrives with the box.

## What the parity ledger says about this

Nothing, and that is worth knowing: `config` now carries a control, so its
exemption line is gone. The ledger is per-op and cannot express *half an op* —
the read is surfaced and the write is not, and this ball is the only record of
that.

---

## The ruling: the fan was never a rule about workspace-less gestures

Shape 1 was taken, but not as the ball framed it. It is not a third arm saying
*this act names a channel*, and it is not a "don't fan" flag.

The poster's predicate establishes one thing — a gesture with no `workspace`
**cannot name a channel by its workspace**. *Therefore every channel is its
subject* was a second step the poster took on its own. That step is true of a
window-level READ, whose subject genuinely is the box's whole set, and false of
a `config` write about one engine's own file. So the address stops being
inferred: `crate::ui::Posted` carries the channel a gesture is addressed to,
and **the fan is what addressing it to no channel in particular means** — the
general path with empty input rather than a branch. `tick` gained no arm; the
loop body reads `legs(&standing, &posted)`, which is the named channel or every
held one.

Where the address is recorded is settled by the file it lives in: `Posted`
already carries `act`, which its own doc says *cannot be computed* and is
*recorded at the control*. This is the same fact one field over — and the
poster deliberately does not read the aim on the send pass (bl-c70d), because
an operator may compose one gesture aimed at a wall on one channel and fire
another at a row on a second before either leaves.

Shape 2 (refuse the engine's globals) costs the operator the three files they
most want to edit. Shape 3 (carry the aimed workspace anyway) is the seat
asserting a thing about a file that is not true of it. Neither was taken.

**The write is then addressed exactly as the read already was**, and the branch
is one predicate read twice (`Where::addresses_a_workspace`): a destination
naming a workspace is routed by it — which is what performs an entry's rename
at the channel boundary, and what naming a channel would bypass — and one
naming the engine goes down the aimed channel by name.

## The destructive question: ordinary, and the box is why

DESIGN §4.20's idiom — a PLACE, a covering pane holding nothing else — is for
an act whose subject ceases to exist. This one's subject is a file that still
exists afterwards, and the control cannot be reached by a mis-aimed click
because reaching it means having authored the file's whole text. So it takes
§4.20's other half, the ENABLEMENT: `write` and `revert` are dark until the box
differs from what the engine last answered, with the refusal spelled beside
them. `revert` is what makes §4.20's own test — *undone by doing the other
thing* — true rather than claimed: the other thing is on the glass beside it.

**What is not ordinary is the guard the wire dropped.** Upstream's editors carry
a hash guard because a long-lived RAM draft can be written over a file that
moved under it; a `config` act carries none and *needs* none because a gesture
states its whole text in one atomic instruction (REMOTE §9.18). True of the
gesture, false of the operator, who types for minutes while a standing read
replaces the answer underneath them. `Draft::seed` — the bytes the box and the
engine last agreed on — restates that guard as a READING rather than a refusal:
the file is neither what the box holds nor what the two last agreed on, which
leaves one reading, another writer. Our own write in flight is excluded (the
answer is still the anchor) and our own write landed is excluded (the answer IS
the box). The engine stays the only thing that judges.

**Nothing records that a write is in flight, and that is the enablement working
rather than a gap.** The control asks *is there anything to write*, a fact about
the world, and stays correct while a write crosses. A flag saying *asked* would
be a second opinion about a question the standing read answers every beat, and
the worst it prevents is writing the same bytes twice, which is the same file.

## The other three questions

- **The box.** `crate::ui::keys::BOXES` goes 3 → 5: the editor's box and the
  workflow name box.
- **`litany-workflow` arrives with it**, and the box IS the listing rather than
  a control asking the operator to remember: upstream mints the file on a name
  it has not seen, so no listing can exist. Empty names no destination and the
  control beside it is dark.
- **A successful write answers `{"ok":true,"kind":"applied"}`**, which this
  build decodes as no kind and paints as §4.9's rung-3 notice — the same thing
  `delete-workspace` has done since §4.20, and a fact about the reply vocabulary
  rather than about this pane.

## What landed

`verbs::write` (one envelope with the read, `text` the whole discriminator),
`Posted::down`, `poster::legs`, `Draft` with its two readings,
`Model::{draft_config, draft_box, drafted, revert_config, write_config,
workflow_box, workflow_named}`, `Model::channel` (which `login::elsewhere` now
reads too rather than repeating the lookup), and the pane split three ways
along a real seam — *which file* / *what the engine reads in it* / *what this
operator would put in it instead*. DESIGN §4.30 rewritten, §4.21 amended where
its inference narrowed, five §5 map rows. `parity.toml` loses no row — the read
already deleted them — and its comment now says the other half exists.
