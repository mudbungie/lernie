Operator ruling, 2026-07-27, verbatim:

> So it's in git? we shouldn't ship _any_ configurations like that to git. The
> actual source should have nothing but protocols and urls to trigger the login
> workflow. This is actually the kind of thing that I want ripped out of history.

## What is in git

`install/models.yaml`, committed, clean tree, 6 commits of history. It declares
policy — which models exist, who serves them, what they can do:

    models:
      claude-sonnet-5:
        provider: anthropic
        model_id: claude-sonnet-5
        capabilities: [tool_use_native, prompt_caching, streaming, stop_sequences]
        context_window: 1000000
      claude-haiku-4-5:
        provider: anthropic
        …

`lernie prime` seeds it to the config root, and it reaches yog too: yog founds
its nested world by invoking `lernie prime` rather than reproducing the seed
(yog DESIGN §16.6 W3), so every yog install inherits this file verbatim.

Its last touch was `88dc127` — *"Invalid model id claude-sonnet-4-7 shipped as
worker default; no live call ever caught it [bl-3157]"*. Same class of bug,
fixed once at the value level. This ball is the structural version: the values
should not be here to be wrong.

## The principle, and the proof it is achievable

Mark's AGENTS.md: *"Severability test: removing a default should delete config,
not edit code — policy lives in the capability, not the core."*

**brazen already does this correctly** — use it as the reference, not as a
comparison. `~/dev/brazen/data/defaults.toml` (84 lines) ships only mechanism:

    [[provider]]
    name       = "anthropic"
    base_url   = "https://api.anthropic.com"
    api_header = { name = "x-api-key", scheme = "raw" }
    model_prefixes = ["claude-"]

Protocol, URL, auth shape, routing prefix. **No model is named.** That is the
shape the operator is asking for, and brazen proves lernie can have it.

## What that means for lernie

`models.yaml` exists because lernie needs facts brazen does not publish —
per-model `capabilities` and `context_window`. Measured this session:
`bz --list-models --provider codex --json` returns only `{"id":…,"default":…}`.
So the file cannot simply be deleted; the question is where its content comes
from when it is not a git-committed table.

Settle at least:
- Does lernie ship an **empty** `models.yaml` (a commented template naming no
  model) and let `bz --list-models` plus the login flow populate it?
- Or do capabilities/context_window move to brazen, which already owns the
  provider contract and could publish them?
- Or does lernie stop requiring them — `config::cross::check_roles_against_models`
  is currently a hard refusal, which is what makes an undeclared model fatal
  (see yog bl-5426, which had to write `models.yaml` entries to avoid bricking a
  workspace). If the refusal softened, the table stops being load-bearing.

The third is the subtraction answer and deserves the first look.

## On "ripped out of history" — read before doing it

The operator asked for a history rewrite. Do it with these facts in hand:

1. **There are no credentials in this file.** It is model ids, capability lists,
   context windows, and provider names. Nothing secret has leaked. The
   justification is architectural hygiene, not incident response — so weigh the
   cost honestly rather than treating it as urgent containment.
2. **lernie 0.0.2 is published to crates.io.** A git history rewrite does not
   retract a published `.crate` tarball; `install/models.yaml` remains in every
   published version forever. If removing it from distribution is the actual
   goal, that needs a yank/republish decision, not a rebase.
3. **yog pins `lernie =0.0.2`** (yog bl-4014). A rewrite plus republish moves
   that pin.
4. **The remote has merge history** (`ceee487`, PR #2 from release-plz). A
   rewrite means force-pushing a public branch: every clone, every `bl` work
   worktree under `$XDG_STATE_HOME/balls/plugins/…`, and any CI checkout breaks
   and must be re-cloned.

Recommended order: land the structural fix first so the file stops carrying
policy going forward; then decide the history rewrite separately, with the
publish question answered. Do not rewrite history as step one — if the shape of
the replacement changes what should have been committed, the rewrite gets done
twice.
