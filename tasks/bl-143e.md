lernie's `Cargo.toml` line 13 pins `brazen = "=0.0.2"`. brazen 0.0.3 has been published to crates.io (it is the crate's default_version; brazen's local main is also 0.0.3, with an open release PR for v0.0.4).

## Why this bites

lernie enforces the pin at runtime — the e2e tests fail with:

    lernie prompt: bz version "0.0.3" does not match the linked brazen crate "0.0.2"
    (§4.4 — install the pinned binary: cargo install brazen --version =0.0.2)

So anyone whose global `bz` is current (or built from a local brazen checkout) cannot run `make ci` without DOWNGRADING their machine-wide `bz` to 0.0.2. That already happened once during the bl-2e35 work: an agent followed the error message's instruction and replaced /home/u/.cargo/bin/bz with the 0.0.2 release. The check is correct to exist; the pin it enforces is just out of date, so the check pushes people to break their environment instead.

Confirmed pre-existing: the 5 e2e failures reproduce on unmodified main with a clean tree.

## The work

Bump the pin to `=0.0.3` and make whatever source changes brazen 0.0.3 requires. Note brazen 0.0.3 is a BREAKING release — its Cargo.toml describes it as the "harness wave: count-tokens/output/Document/raw-split/--timeout (breaking)" — so this is not a version-number-only edit. Read brazen's CHANGELOG before starting.

Verify with `make ci` green against a `bz` 0.0.3 on PATH.

## Worth deciding at the same time

Whether an exact `=` pin on a dependency that is also a globally-installed binary is the right shape at all, given it forces a machine-wide install to match a per-repo lockstep. That is the actual design question behind the recurring pain — a floor plus a compatibility assertion may serve better than exact-match. Do not change it without a ruling.
