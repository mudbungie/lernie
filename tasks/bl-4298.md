Deliverable: `docs/ARCHITECTURE.md` §2.11/§2.6 edits closing the open questions below, then implementation balls. Living document.

## Status

The entire messaging substrate is **spec-only**. `grep -rn inbox src/**/*.rs` returns zero hits: no `inbox/` directory, no `message` built-in tool, no `lernie message` verb, no flock-on-inbox-fd executor lock, no delivery commit, no deposit-starts-a-driver. §2.11 is written; nothing implements it.

It is the prerequisite for everything: bl-65d8 makes the inbox the *only* return path, and bl-4ce8 (delete `merge/`) cannot be claimed until it exists.

## Why this is a design ball, not an implementation ball

§2.11 was written before bl-65d8 dissolved `await`. Three questions it does not answer:

**1. Where do the result message’s fields live on disk?** bl-65d8 gives every result message three fields: terminal ref, **epitaph** (pinned manner of ending), and terminal response (iff the agent spoke). A delivered message lands as `messages/NNN-<sender>.md` (§2.3:184). But §2.3:192 rules that role framing is *"derived from the path, not from frontmatter"* — so is frontmatter admissible for terminal-ref/epitaph, or does that rule generalize? An answer is needed, and "the path" cannot carry three fields.

**2. What triggers the sweep?** bl-65d8 makes §8’s silent-death enumeration (`:812`) *deposit* an epitaph for hard-crashed agents, not merely count them. §8 is a metric read on demand; a depositor needs a trigger. Every `lernie` invocation? Only drivers? This must not become a resident watcher — §2.11:373 forbids one (*"No abandonment, no takeover, no watcher left behind"*).

**3. Executor lock: flock vs. the shipped `/proc` scan.** §2.11:371 specifies `flock(2)` on the agent’s inbox directory fd (*"Liveness is observed, not stored, and there is no stale-lock cleanup because there is nothing on disk to go stale"*). Shipped code instead scans `/proc/<pid>/fd/*` for an open `response.json` (`await_tool/state.rs:145`) — Linux-only, and it survives for `lernie stop` (§2.9) and §3.5 `in_flight` regardless. Are these one mechanism or two? Decide before building.

## In scope

- The three questions above.
- `lernie message <workspace> <agent> <content>` (§3.4) and the `message` built-in (`{agent, content}`, returns `{status: deposited}`).
- Deposit: `<workspace>/inbox/<agent-id>/<sender>-<NNN>.md`, create-only, temp-path + atomic rename (§2.11:354).
- Delivery: step-boundary drain into `messages/<NNN>-<sender>.md`, one delivery commit (§2.11:360).
- Deposit-starts-a-driver for a quiescent recipient (§2.11:358); writer/driver totality (§2.11:373).

## Out of scope

- The return path itself (bl-4ce8) — this ball builds the channel, that one uses it.
- `await`/`check` — deleted by bl-65d8 / bl-2ca1. Do not build them.
