## The defect

`prompt::dispatch::advance::warrant` reads the **last** message only:

    fn warrant(messages: &[Message]) -> Warrant {
        match messages.last() {
            None => Warrant::NothingDue,
            Some(m) if matches!(m.role, Role::User | Role::Tool) => Warrant::ModelCallDue,
            Some(m) if m.content.iter().any(|b| matches!(b, Content::ToolUse { .. })) =>
                Warrant::Unpaired,
            Some(_) => Warrant::NothingDue,
        }
    }

`Warrant::Unpaired` — "the one non-replayable state (§6), declined loudly" — is
therefore only reachable while the unpaired assistant entry is the tail. The
hop's own ordering guarantees it usually is not: `driver::deliver` runs
**before** `warrant`, so any pending deposit is committed user-side first. The
tail is then `Role::User`, the warrant is `ModelCallDue`, and the request
carries an assistant `tool_use` with no `tool_result` behind it.

The provider rejects it, every time, forever:

    {"type":"error","kind":{"provider":{"status":400}},
     "message":"No tool output found for function call call_mpqKdUY7N9uQ8DpY6tUvBDnt."}

Observed on two agents in a yog workspace on 0.0.6. The loud decline the code
intends never printed; the operator saw a conversation that had simply stopped
answering, and every further message reproduced the 400.

## Why the hold path is not the answer

`advance::run` already knows this hazard and guards exactly one case:

    // A hold mark parks the branch mid-tool-window (§3.3 *Tool control*), and
    // the held entry runs **before delivery** — mail delivered onto an unpaired
    // tail would wedge between a `tool_use` and its `tool_result` (§2.3
    // pairing), so a parked branch queues its mail instead ([`held`]).

That is the same wedge, and the mark is what makes the park legible. A window
that died *without* writing a mark (a crash, an OOM kill, a control fault) has
no mark to gate on — and that is the §6 non-replayable state the decline exists
for. Delivery order silently disarms it.

## Shape of the fix

Derive the warrant from the alternation, not the last element: an assistant
entry whose `tool_use` ids are not all matched by committed `tool_result`s is
`Unpaired` **wherever it sits**, mail behind it or not. bl-b98d's settlement
already gives the interrupted-window case a resumable tail, so after this the
`Unpaired` arm names only genuinely non-replayable states — which is what it
was always documented to mean.
