Found while landing bl-8366. Under a plain `cargo test --lib` (default parallelism, loaded box) these two failed intermittently — 2 of 3 consecutive runs:

- `cmd::tests::verbs::config_reports_a_declined_pass_as_a_clean_line` (src/cmd/tests/verbs.rs — the second pass returned something other than `Outcome::Line`, i.e. it was NOT declined: something changed between the two no-op editor passes)
- `cmd::tests::verbs::config_authors_a_commit`

Both passed in isolation and both passed under the gate, because tarpaulin.toml pins `--test-threads=1`. So the gate never saw it, and it was not a delivery blocker — but it made bare `cargo test` an unreliable signal for anyone iterating, which is how it was found.

NOT the bz/PATH class of failure (bl-8366): reproduced with the ambient and the pinned adapter alike, and these tests never exec `bz`. Sibling flakes: bl-2061, bl-9300 (spawn_retries_past_transient_etxtbsy).

--- RESOLVED (Tiller diagnosed + implemented; Chock reviewed; Thimble re-verified and landed) ---

CONFIRMED MECHANISM: `config::run` calls `harness_root::resolve()` (src/harness_root.rs) directly and unmocked, which reads the process-global `LERNIE_HOME` env var. The two `config_*` tests read this ambient value with no isolation at all, so `roots.data` resolved to whatever the process's real environment was at that instant — on a dev box, the real `~/.local/share/lernie` pool.

The crate already had one guarded mutator of this process-global var: `with_lernie_home` in `src/cmd/tests/mod.rs`, serialized by a `Mutex` (`ENV_LOCK`), used by `new`/`prime` tests. But (a) the two `config_*` tests never went through it, so their reads raced the ambient value against every other test's `with_lernie_home` window, and (b) a *second*, entirely unguarded mutator existed: `src/e2e/bundle_replay_cli.rs::replay_cli_lands_under_lernie_home` called `std::env::set_var`/`remove_var` directly, justified only by a stale comment ("SAFETY: single-threaded test run (tarpaulin.toml --test-threads=1)") — true for the gate, false for bare `cargo test --lib`.

Proved with instrumentation (eprintln'd thread id + `LERNIE_HOME` value at each `harness_root::resolve()` and `commit_checkout`, later stripped): wrapping only the two `config_*` tests in `with_lernie_home` was NOT sufficient — the declined-pass test's second pass still observed `LERNIE_HOME=None` mid-closure (lock held) because `bundle_replay_cli.rs`'s unguarded `remove_var` fired concurrently, outside `ENV_LOCK` entirely, yanking the var out from under the guarded window. The pool that then leaked in on the "declined" pass matched byte-for-byte the real ambient pool (`~/.local/share/lernie/{tools,skills}`: bash, dispatch, load_skill, message, read_file) — direct confirmation of the ambient-env-leak theory, not the "§3.3 refresh is order-sensitive" alternative.

FIX AS LANDED (test-side only, no production change): consolidate every in-process `LERNIE_HOME` mutation onto one shared, lock-guarded helper.
- Moved `ENV_LOCK` + `with_lernie_home` out of `src/cmd/tests/mod.rs` into `src/test_support.rs` (already the crate's shared in-process test-helper module, `#[cfg(test)]`, non-`pub` at the crate root), made `pub` within it.
- `src/cmd/tests/verbs.rs`: `config_authors_a_commit` and `config_reports_a_declined_pass_as_a_clean_line` wrap their `config::run` invocation(s) in `with_lernie_home(scratch_dir, ...)` — the declined-pass test wraps *both* passes in one call so they share one lock-held window and see an identical (empty) data root.
- `src/e2e/bundle_replay_cli.rs::replay_cli_lands_under_lernie_home`: raw `set_var`/`remove_var` pair replaced with `crate::test_support::with_lernie_home` (the same bug's second, silent instance).

No production code touched (`harness_root.rs`, `config.rs`, `template/*` all unchanged) and no assertion weakened — `Outcome::Quiet`, the `config/default unchanged: ` prefix, and the `.config-author` absence check are all preserved verbatim. This was purely a test-isolation gap, not a behavior bug.

Net delivered diff: 4 files, all test-side — `src/cmd/tests/mod.rs`, `src/cmd/tests/verbs.rs`, `src/e2e/bundle_replay_cli.rs`, `src/test_support.rs`.

DETERMINISM EVIDENCE (three independent campaigns, all at default parallelism on a box under concurrent sibling load):
- Tiller: 44 consecutive `cargo test --lib` runs, 0 failures across `config_authors_a_commit`, `config_reports_a_declined_pass_as_a_clean_line`, `replay_cli_lands_under_lernie_home`.
- Chock (review re-verification): 25 consecutive runs, same three tests, 0 failures.
- Thimble (post-`git merge main` end state): 10 consecutive runs, all three green every run — and every run exited 0, i.e. the *entire* 924-test lib suite passed 10/10, including the known-elsewhere flakes parent_revival / sweep_deposits_died (bl-7318, not this ball).

ALIGNMENT: terminology swept — one bare "call" in the moved doc comment ("never observes another call's home") violated docs/ARCHITECTURE.md §2.1 Banned usage ("**\"call\"** without a qualifier — use model call, tool call, or API call") and was requalified to "another test's home". `LERNIE_HOME` / harness root / data root are used in their §2.2 senses. Test-only change, so no doc surface moves.

Gate: `make check` green at the end state (fmt-check, clippy `-D warnings`, tarpaulin 100.00% coverage 4857/4857 lines with +0.00% change, install contract), plus the pre-commit hook's own independent green run.
