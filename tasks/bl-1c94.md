## What the docs promise

README ("Dispatching subagents directly"): "The compaction merge lands
later and elsewhere: when the compactor's result message is delivered,
the dispatching agent's own executor interprets its `compactor_return:
compaction_merge` binding (§6) and merges the compactor branch `--no-ff`
... A compactor that ends on any other epitaph lands no merge; the
branch simply continues uncompacted."

ARCH §2.6/§2.11 similarly gates driver relaunch on epitaph value ("a
final response launches; `stopped` and `budget-exhausted` never do").

## Repro (live wire, follows directly from bl-f021's scenario)

Using the same workspace/scenario as bl-f021 (compactor dispatched
automatically via `n: 1` checkpoint, its first model call errors
non-retryably and it crashes without ever running its exit handler):

1. `lernie scan <ws>` — first pass reports `silent deaths: 1; died
   deposits swept: 1; drivers launched: 1`. The scan's silent-death
   sweep classifies the compactor child as dead (no live executor, no
   result ever deposited — it's a child) and deposits a `died`-epitaph
   result message into the parent's inbox on the child's behalf, then
   launches a driver at the parent to flush it.
2. That driver delivers the `died` message. `git -C repo.git log
   --oneline --graph agents/<parent-id>` then shows a NEW commit:
   `commit 956bfa1 (merge, 2 parents) "compaction merge
   [<compactor-id>]"` — a real `--no-ff` merge of the compactor branch
   into the parent, even though the compactor's epitaph was `died`, not
   `final-response`, and it never wrote a summary or called
   `mark_for_deletion`.

## Root cause (src/prompt/dispatch/child_result.rs)

`child_event` (child_result.rs ~L148) derives the workflow event purely
from the returning child's ROLE (compactor -> `Event::CompactorReturn`),
never reading `cr.epitaph`. `child_actions` maps `CompactorReturn`
unconditionally to `vec![Action::CompactionMerge]`, and `execute_child`
runs it. The epitaph-gate that ARCH §2.11 describes (`exit_launch` in
src/prompt/dispatch/terminal.rs ~L125) only gates the SELF-RELAUNCH /
PARENT-REVIVAL driver-spawn decision, and by its own comment explicitly
never sees `died` at all ("died never reaches an exit path at all: a
dead executor runs nothing") because the scan sweep deposits `died`
directly, bypassing `exit_launch` entirely. Nothing re-checks epitaph
before firing `compaction_merge` on delivery.

No test covers this: `child_result/tests/cases.rs
a_compactor_result_lands_the_compaction_merge_and_consumes_the_message`
only exercises a normal `final-response` return. Nothing under
src/prompt/compactor/, src/prompt/dispatch/, or src/e2e/ asserts "a
died/stopped/budget-exhausted compactor return lands NO merge."

## Why this matters

The compactor's whole safety argument (README/ARCH §2.6: "the worst case
is lost information, never corrupted information") rests on the merge
only landing after a clean, complete compaction pass. This bug lands the
merge on ANY compactor return regardless of how it ended — in this
repro it was a no-op merge (the compactor deleted/wrote nothing before
dying), but nothing in the code prevents a compactor that died
mid-work — after some `mark_for_deletion` calls landed on its own branch
but before it finished and spoke — from having those partial changes
merged into the live parent, which is exactly the "corrupted, not just
lost" outcome the deletion-only toolset was designed to make impossible.

Given bl-f021 makes a compactor's FIRST model call fail routinely
whenever the dispatching branch already used a tool (the common case,
since checkpoints only fire "closing a tool step"), this isn't a rare
combination — the two bugs compound to make silent, unintended merges a
realistic outcome of ordinary compaction, not a contrived edge case.

## Expected

`child_actions`/`execute_child` (or wherever the delivered result's
epitaph is available) should skip `Action::CompactionMerge` for any
epitaph other than `final-response`, matching the documented rule and
the `exit_launch` precedent for driver relaunch.

## Resolution (Bosun, 2026-07-26)

Fixed as specified, delivered together with bl-ee80 on work/bl-1c94
(commit "Epitaph-gate compaction_merge; classify failed model calls as
silent deaths [bl-1c94][bl-ee80]").

- `child_result::execute_child` now gates `Action::CompactionMerge` on
  the delivered result's epitaph value (`merge_qualifies`): only
  `final-response` merges, matching README/ARCH §2.6-§2.7 and the
  `exit_launch` precedent. The gate is on the ACTION, not the default
  binding, so no workflow config can merge an unfinished compactor.
- A non-qualifying compactor return falls back to `deliver_result` —
  the ordinary child return (work-product transfer + transcript
  delivery) — so the parent sees the epitaph in its transcript (§2.7
  "surfaced for user review like any other child failure") and the
  branch continues uncompacted. Nothing of the compactor's tree crosses
  (summary/** and messages/** are excluded context in the transfer).
- Tests: `a_died_compactor_return_lands_no_merge_and_delivers_the_epitaph`
  (no merge commit, no summary crossing, epitaph delivered, inbox
  consumed) and
  `a_stopped_compactor_return_lands_no_merge_under_an_explicit_binding`
  (explicit `compactor_return: compaction_merge` binding equally gated).
  Parent revival is the flush/probe seam, epitaph-agnostic, already
  pinned by the scan tests. Docs: ARCH §2.6/§2.7/§6 notes and README
  amended to record the enforcement point.
