## Repro (live wire, codex/gpt-5.4 provider)

1. `lernie new <ws>`, then `lernie config <ws>` with EDITOR script setting
   `providers.yaml` roles.worker/compactor to provider `codex` model
   `codex-gpt54` (models.yaml entry: provider codex, model_id gpt-5.4),
   and `workflow.yaml` `compaction.intermediate.trigger: every_n_commits`
   `n: 1` (so a checkpoint fires after the very next tool step).
2. `lernie prompt <ws> 'Use the bash tool to run `echo hello-from-tool` and
   then tell me what it printed.'` — the worker calls `bash`, gets the
   result, replies with text. This step closes as a tool step, so per
   README ("Closing each tool step, the executor reads the compaction
   checkpoint clock") the `n: 1` trigger fires and dispatches a compactor
   automatically (`worker_flush: dispatch(compactor)`).
3. The compactor child is spawned and its dispatch message is delivered
   (`transcript 004: <parent-id>` lands on the child). Its own first model
   call — `steps/<child-id>/001/response.json` — immediately errors:
   `{"type":"error","kind":"parse_input","message":"tool accepts only
   text content","provider_detail":null}` then `{"type":"end"}`. The
   compactor never writes a summary, never calls a tool, never speaks.

## Root cause (read from steps/<child-id>/001/request.json)

The compactor forks with its parent's transcript inherited in its tree
(ARCH §2.3 "Fork and inheritance" — by design, no special channel), so
the assembled wire history includes the parent's `tool_use`/`tool_result`
pair for `bash` (the tool that triggered the checkpoint in the first
place). But per README/ARCH §2.7, "Its injected toolset is exactly
`write_summary` and `mark_for_deletion` ... available to that role
alone" — `bash` is never declared in the compactor's request `tools:`
array. The provider (codex, protocol `openai_responses`) rejects a
`tool_use`/`tool_result` pair referencing a tool absent from the
declared `tools:` list.

## Why this matters

Per README, the compaction checkpoint clock is read specifically
"closing each tool step" — i.e. a checkpoint can only fire right after a
tool call landed in the transcript. So in the ordinary/expected case, by
construction, every real compaction dispatch inherits a transcript that
ends in a tool_use/tool_result pair for some tool NOT in the compactor's
fixed toolset. This makes the compaction path fail its very first live
model call in what is close to the common case, not an edge case — and
per docs/USER_STORIES.md US-18 / G4, no test has ever landed a
compaction merge end-to-end through a real model call, so this was
previously unverified in this exact shape.

Not the known brazen bl-fba7 gap (that's `local`/ollama_chat
unconditionally rejecting any `tool_result`, regardless of tool
declaration) — this reproduced against the `codex` provider
(`openai_responses` protocol), specifically because of the undeclared
tool name in history, not tool_result content in general.

## Expected

Per ARCH §2.7, the compactor should be able to read/summarize a branch
that used tools without the wire rejecting its very first call. Either
the compactor's canonical request needs to declare the inherited tools
(read-only, non-callable) so the wire's referential integrity holds, or
the request construction needs to strip/rewrite tool_use blocks whose
tool isn't in the compactor's own toolset before sending.
