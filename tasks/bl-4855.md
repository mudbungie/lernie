bl-5c53 landed the read half: the lineage listing, the five destinations as one
typed `Where`, and a pane that paints a config file's bytes beside the settings
the engine's schema found in them (DESIGN §4.29). What it did not build is the
write, and the reason is a hazard rather than time.

## The write is one field, and the field is not the problem

`config` is one op that is a read or a write depending on whether it carries
`text` at all (upstream's own discriminator, REMOTE §8.5). So the act is the
read's envelope plus the whole new text:

    {"op": "config", "target": <the same target the read carries>, "text": "…"}
      -> a file destination answers the path written; a lineage answers
         `litany config`'s captured run (`reply/outcome`, already painted)

## The hazard: three of the five destinations name no workspace

`litany-models`, `litany-workflow` and `cadence` are the ENGINE's own files and
carry no workspace anywhere in the envelope. This seat's poster fans every
gesture that names no workspace — `crate::offframe::poster`, bl-40ec — so an
ACT composed for one engine's `cadence.yaml` would be sent down **every channel
this box holds**, writing the operator's text onto every engine they are a
client of. The read half dodges it by not posting at all: a standing read is
asked down the aimed channel by name.

Three shapes to attack before writing a line of it, and the ball should record
which was taken and why:

- **Post through a channel-addressed door.** The poster's split is
  `workspace present → route, absent → fan`; a third arm — *this act names a
  channel* — is a new mechanism on the one queue REMOTE §3's *sent exactly once*
  rides on.
- **Refuse to write the engine's globals from a seat**, and offer the editor
  only for the two destinations that name a workspace. Subtraction, and it costs
  the operator the two files they most want to edit.
- **Carry the aimed workspace in the target anyway.** Upstream's `decode_file`
  ignores unknown keys, so it would route correctly and be ignored on arrival —
  and it is the seat asserting a thing about a file that is not true of it.

## The other three questions the write raises

- **Is it destructive?** It replaces a file's whole bytes and a lineage write is
  a commit. DESIGN §4.20's idiom (an arming that is an enablement, and an
  unmaking that is a place) exists for acts that cannot be undone by doing the
  other thing; a config write can be undone by writing the old bytes back, which
  the pane is holding. Decide whether that makes it ordinary, and say so.
- **The editor needs a box**, and `crate::ui::keys::BOXES` is the whole list of
  boxes that take text — a fourth joins it in the commit that paints it.
- **`litany-workflow` has no read either**, because it is addressed by a name
  and nothing lists what names exist. It arrives with the box.

## What the parity ledger says about this

Nothing, and that is worth knowing: `config` now carries a control, so its
exemption line is gone. The ledger is per-op and cannot express *half an op* —
the read is surfaced and the write is not, and this ball is the only record of
that.
