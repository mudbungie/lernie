Operator report 2026-08-02 (from yog): a conversation with agent vision-kiwi showed the bash tool definition is way too unclear — the model believed it was talking to a server-side interactive bash prompt. Operator: 'Have an agent take a look at what codex is doing. I've never had an issue there.'

## Evidence: the literal misunderstanding

Conversation `~/.local/share/yog/workspaces/ops/agents/20260801T231907Z-3200c2c2/`, agent `vision-kiwi`, model `gpt-5.6-sol`. Asked "can you find my ip address?" it never considered running the tool. Verbatim, in order:

- 004: "I can't see your IP address through this chat." — offers the user `curl https://icanhazip.com` to run themselves.
- 006 (user: "yeah, get it"): "I can't retrieve your IP from this chat—**the shell available to me would only show the server's IP, not yours.**"
- 008 (user: "you have a bash tool, don't you?"): "**Yes, but it runs on the remote agent environment—not on your device.** Running `curl ifconfig.me` would reveal that server's public IP, not yours."
- 010 (user: "no, the bash tool is local"): finally calls `bash` with `curl -fsS --max-time 10 https://api.ipify.org`. It works, returns `203.0.113.146`.
- 012, after the correct answer is in hand: "The environment reports its public IP as 203.0.113.146. **If this Bash tool truly runs on your local device/network, that is your public-facing IP. Otherwise, it belongs to the tool's execution environment.**"

The wire request (`steps/20260801T231907Z-3200c2c2/005/request.json`) carried exactly this, and nothing more:

- `tools[0].description`: "Run a shell command via `sh -c` and return its stdout. Use for filesystem inspection (`ls`, `find`, `head`), text processing (`grep`, `sed`, `awk`), version-control queries (`git log`), and anything else that fits a one-liner. The command's stderr is surfaced only when it exits non-zero."
- `tools[0].input_schema.properties.command.description`: "Shell command to execute via `sh -c`. The string is passed verbatim; quoting and escaping are the shell's job. Stdout becomes the tool result; stderr is concatenated after stdout when the command exits non-zero (ARCH §3.3 stdio contract)."

Neither string says *where* the shell runs, that it is one-shot, or that there is no TTY. Every hedge in the transcript is a fact the definition left open.

## What codex actually does (openai/codex `main`, verified against source)

Not what the old lore says. The argv-array `shell` tool is **retired**. Current `main` registers `shell_command` (a plain `type: "function"` tool) for every model in `models-manager/models.json` — all 8 rows declare `"shell_type": "shell_command"`, `gpt-5.6-sol` included.

- name: `shell_command`; `strict: false`; `required: ["command"]`; `additionalProperties: false`.
- description, verbatim (2 lines): "Runs a shell command and returns its output." / "- Always set the `workdir` param when using the shell_command function. Do not use `cd` unless absolutely necessary."
- `command` is a **single string**: "Shell script to run in the user's default shell." Optional: `workdir` ("Working directory for the command. Defaults to the turn cwd."), `timeout_ms` ("Maximum command runtime. Defaults to 10000 ms."), `login`, `sandbox_permissions` (enum `use_default` / `with_additional_permissions` / `require_escalated`), `justification`, `prefix_rule`, `additional_permissions`.
- No `output_schema` reaches the model (`#[serde(skip)]`). The result is plain text: `Exit code: N` / `Wall time: X seconds` / optional `Total output lines: N` / `Output:` / middle-truncated **aggregated stdout+stderr** (they are not separated for the model). Non-zero exit is returned as a tool *error*.
- The retired `shell` (tag rust-v0.44.0) is where `command: string[]`, `with_escalated_permissions`, `justification` lived; `local_shell` (`{"type":"local_shell"}`, zero schema, server-side, `codex-mini-latest` only) is also gone from the declaration path.
- Interactivity is structural, not prose: behind a feature flag codex ships `exec_command` (PTY, returns a `session_id`) + `write_stdin`. Nothing in codex ever *says* "non-interactive" about the shell.

**Why codex never confuses the model, and it is not the description.** "Runs a shell command and returns its output." is barer than lernie's was. Codex answers the environment question in a different channel: an injected `<environment_context>` block (`<cwd>`, `<shell>`, `<current_date>`, `<timezone>`) plus a `<permissions instructions>` developer message naming the sandbox mode ("`sandbox_mode` is `workspace-write`: … Network access is enabled."). The frame is asserted before the model ever reads a tool.

lernie has no such channel — ARCH §5.1: a branch's assembled body *is* its worktree (goal, soul, transcript), all operator-authored. So the tool definition is the only place the frame can live, and it must carry it.

## Decision: keep the schema, rewrite the prose

**Schema unchanged** — one required `command: string`, `additionalProperties: false`. Justification:

1. Shape already matches. Codex's *current* tuned shape is a single `command` string, same as lernie's. The argv array people remember is the retired tool. There is nothing to converge on.
2. `workdir` would be a lie. ARCH §3.3 *Working directory* fixes every tool's cwd to the calling agent's worktree by construction, precisely so side effects land on the branch. A `workdir` param either does nothing or breaks that invariant.
3. `timeout_ms` would be a lie. lernie imposes no wall-clock limit at all — `DEFAULT_TOOL_DEADLINE` (5s) is the SIGTERM→SIGKILL grace after a *cancel*, not a run limit.
4. `sandbox_permissions` has no referent: lernie has no sandbox.
5. `prompt::tool::builtin::bash::Input` is `deny_unknown_fields`, so any param added to the schema and not to the executor is a promise refused at runtime.

**Prose rewritten** to assert four things the old wording left open: local, non-interactive, worktree-rooted, stateless between tool calls.

## What landed

- `skills/bash/SKILL.md` — new frontmatter `description` (the wire string) + body sections "Where it runs", "It is not an interactive shell", "State between tool calls". Also corrected a false claim in the old body: it said the SIGTERM cascade "fires after the harness deadline", implying a timeout. It fires on cancellation only.
- `schemas/tools/bash.json` — `command` description now states `sh -c` on *this machine*, stdin `/dev/null`, no TTY, runs to completion, starts in the worktree, shell state discarded on exit.
- `docs/ARCHITECTURE.md` §3.3 — note after Tool point 3: a tool definition is the only frame lernie ships; the codex contrast; the four claims; why the schema is unchanged.
- `README.md` — bash built-in bullet points at the new definition and the finding.
- `src/install/tests/` — `tests.rs` split to `tests/mod.rs` + new `tests/toolspec.rs` (per-file line cap), four tests pinning the four claims in the *wire* strings (frontmatter parsed through `skill::parse`, schema through `serde_json`) and pinning the one-string schema shape.

## Observed, not fixed (candidate follow-up)

lernie's `tool_result` carries stdout plus (on failure) stderr, and `is_error` — the **exit code itself never reaches the model**, and stderr on a zero exit is dropped silently. Codex surfaces `Exit code: N` and `Wall time` in the result text and aggregates both streams always. That is a §3.3 stdio-contract change affecting every tool, not a bash description fix, so it was left alone here.
