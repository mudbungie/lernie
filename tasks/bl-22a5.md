A running agent is welded to the config it forked off, for life, with no verb to move it. `retarget` is the way out — and it must be built as a **ref mark the executor consumes**, not a merge.

## The trap (observed in yog, conversation `ladies`, 2026-08-07)

An agent's model failed on an expired credential. The operator changed the model. The change landed correctly on `config/default` (`a06b090`) and governed nothing: the agent forked `d93c2a9` two days earlier, and §2.2 derives control from ancestry — "the nearest ancestor of the agent's branch reachable from any `config/*` ref. Derived from ancestry, never stored." The reprompt dispatched the same model and failed identically.

Forking does not escape it either. `src/prompt/fork_point.rs:16-18`:

> the governing config commit is derived from that ancestry like any other agent's ([`workspace::governing_config`]), so **fork is the freeze** whatever the fork point is.

A fork off an `agents/*` commit still merge-bases to `d93c2a9`. There is no ref you can name that carries the history forward onto newer policy. §2.2's "Later user edits advance the config branch and affect only agents forked after them" states the freeze; nothing states an exit, and one is wanted: the operator's alternative is to abandon a live conversation's whole history to change a model id.

## The mechanism — nothing new, two existing patterns composed

**Not a merge.** §2.3's branch-advancement invariant is unconditional: *"A config branch advances only by user config edits; an agent branch advances only by its executor (§2.11). No branch has a second writer, and nothing merges into either kind."* Compaction's `--no-ff` merge — the obvious precedent — was **retired** by bl-bc9c; the landing is a rebase-forward and §2.6 records the result: "leaving no merge anywhere in the system." A retarget merge would reintroduce the one thing that was deliberately removed.

Compose what already exists instead:

1. **The user act is a ref mark, so the single-writer rule is untouched.** `lernie retarget <workspace> <agent-id> [--config <name>]` writes `refs/lernie/retarget/<agent-id>` pointing at the target config commit (default: the head of the agent's own governing lineage). Ref marks as orthogonal, non-derivable state are the established pattern — §6's `mark_abandoned` (`refs/lernie/abandoned/<id>`) and `notify_ui` (`refs/lernie/notify/<id>`), read by the frontend, never pushed to it. The verb refuses a target that is not a `config/*` commit, and refuses one already governing the agent (nothing to do is a clean outcome, not an error).

2. **The executor lands it, at a step boundary, by rebase-forward.** Exactly where and how the compaction landing lands (§2.6): the receiving branch's own executor, at a boundary, replaying the branch onto a new base. Here the new base is the target config commit, so `governing_config` — unchanged, still a pure ancestry query — answers the new commit at the next step. The mark is consumed by the landing.

The legitimacy argument is §2.6's own, verbatim in shape: *"Why this one rewrite is legitimate where merge-back was not is the two-channels polarity — a compactor's payload is the dispatching branch's own context, rewritten on purpose — its payload, not its contamination."* A retarget's payload is the branch's own **policy**, rebased on purpose. Same polarity, same landing, same writer.

3. **The descriptor cut is re-derived, never replayed.** §3.3: the fork's `descriptions/**` cut "is **checked out of the governing config commit**", and "The derivation reads that commit and never the tree it forked off." After the rebase the governing commit is a different one, so the landing re-runs that derivation against the new config for the agent's role (`src/prompt/dispatch/step_commit/descriptors.rs`, the `Grant` triple) rather than carrying the old snapshot forward. A grant the new config does not describe is `Error::GrantUndescribed` — declined at the retarget verb as a pre-flight, before any mark is written, the same validity-before-fork discipline the dispatch pre-flight uses.

## Why the timing is right, not a compromise

The mark takes effect at the agent's **next step**, not on the spot. That is the correct semantics rather than a limitation: a config governs steps, the agent may be mid-step when the operator picks, and the retarget is in practice followed immediately by a reprompt — which *is* that next step.

## Deliverable

- `lernie retarget` (§3.4 verb, one-product convention), its pre-flights, and the mark.
- The landing at the `advance` step boundary, consuming the mark.

- §11 loses nothing: this is not the deferred "live config update" — the freeze still holds by default; what is added is a deliberate, auditable break of it.
