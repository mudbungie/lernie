Requirement from yog phase-2 (crate adoption): yog intends to link lernie as an exact-pinned Cargo dependency instead of shelling to the binary, with the binary remaining as the agent/human tool plane. Two things stand in the way, both lernie-side:

1. ARCH §3.5 currently declares "no library port" — the frontend surface is filesystem + CLI only. That was written when frontends were peers on a shared machine; the embedding-application case (yog owns a nested LERNIE_HOME world and wants compile-time-pinned invocation) is new. This ball is DESIGN-FIRST: amend ARCHITECTURE.md to define what the library surface is (likely: the command entry points — new/config/prompt/dispatch/message/stop/scan/advance/bundle/replay — as pub functions over explicit roots, with the CLI bin becoming a thin argv shim), what it promises (probably: pin-exact, no semver stability at 0.x, same as brazen's posture), and what it deliberately excludes.

2. The driver/successor exec baton: `advance` execs the successor `lernie advance`, and `message` detached-spawns `lernie advance`, both resolving the lernie binary. An embedding application that IS the driver (yog re-exec'ing itself with a driver entry point) needs the successor/driver target parametrized — resolve via current_exe() or an injected binary path, so the host binary carries the loop. Without this, a linked lernie still hard-depends on a `lernie` binary on PATH mid-loop.

Do not start until the init/bootstrap verb ball lands (it touches the same install/seeding surface). Design deliverable is the ARCH amendment; implementation follows it.
