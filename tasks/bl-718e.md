## Operator ruling (2026-08-02, from yog operation)

The turn-rollup aggregate in yog (yog bl-1f21) wants to say '3150 thinking tokens' but cannot: the committed transcript file (`messages/NNN-<model>.json`) is a bare array of brazen Content blocks with NO usage record. Usage (input_tokens/output_tokens) exists only in the diagnostic `response.json` event stream and `steps/` records. The operator has ruled the token counts are good telemetry and should be durable transcript facts.

## What this ball is

When a model call's output is committed to `messages/`, the usage the provider reported rides with it — so any transcript reader (yog's turn rollup, replay, audit) can state real token counts from the committed bytes alone.

## Verify before editing (do not trust this ball blindly)

- `src/prompt/dispatch/transcript.rs::commit_assistant` renames the sealed staging file into `messages/NNN-<model>.json`; `src/prompt/dispatch/staging.rs` writes it as a bare JSON array of blocks (verified against 0.0.3-era tree by yog bl-1f21's builder — re-verify, the tree has moved).
- Where usage lives today: the `response.json` diagnostic stream and `steps/` records.

## Design constraints

- One home: the committed transcript entry. Pick the least-disruptive envelope — the parser contract is 'a bare array of canonical blocks OR an API-shaped object wrapping them in `content`' (yog reads both via one `block_array` answer), so the API-shaped object with a `usage` sibling may already be lawful on both ends; prefer that over inventing a third shape. Whatever you choose, existing committed transcripts (bare arrays, no usage) must keep parsing — absence of usage is the general path, not an error.
- Usage is the provider's report, recorded verbatim — never computed or estimated by lernie.
- Amend ARCH where it specifies the committed transcript shape.
