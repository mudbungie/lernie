## What happens

Any verb that drives a model call, on a machine where `bz` is not on `PATH`,
dies with an errno that names nothing:

```
$ PATH=/usr/bin:/bin lernie prompt /tmp/ws 'hi'
lernie prompt: adapter subprocess: No such file or directory (os error 2)
$ echo $?
1
```

Reproduced against three separately-installed 0.0.1 binaries, all identical:
`cargo install lernie --locked` (crates.io), the `v0.0.1` GitHub release
tarball, and `make install INSTALL_PREFIX=<p>` off a fresh clone of `main`
(commit `6a4a47d`).

## Expected, per the docs

The neighbouring failure — a `bz` at the *wrong* version — is exemplary:

```
$ lernie prompt /tmp/ws 'hi'
lernie prompt: bz version "0.0.9" does not match the linked brazen crate "0.0.4" (§4.4 — install the pinned binary: cargo install brazen --version =0.0.4)
```

It names the binary, the fact, the section, and the literal fix-it command.
`docs/USER_STORIES.md` US-24 promises exactly this class of message for the
adapter seam: *"A **load-time version guard** rejects any `bz` whose
`--version` differs from the linked brazen crate version, **with an actionable
message**."* The absent-binary case is the same guard failing one step
earlier, and it loses all of that.

README §Install step 2 states the remedy the message should carry:
*"Installs the provider adapter — brazen's `bz` — with `cargo install brazen
--version =<pin> --locked`"*, and README §Providers pins it concretely:
*"`make install` installs the pin with `cargo install brazen --version
=0.0.4`."* Nothing of that reaches the user at the moment they need it.

## Why this is the highest-value message in the product

It is the *first* real command for every user who did not install from the
repo. Neither `cargo install lernie` nor the release tarball installs or
mentions `bz` — only `make install` does (Makefile `install-bz`). So the
modal 0.0.1 user's session ends here:

```
cargo install lernie --locked      # ok
lernie new ~/work/chat             # ok, prints the path
lernie prompt ~/work/chat 'hello'  # adapter subprocess: No such file or directory (os error 2)
```

with no thread back to `bz`. Note the released 0.0.1 binary cannot even be
interrogated for the pin: `lernie --version` prints bare `lernie 0.0.1` there
(the `(brazen 0.0.4)` suffix landed after the tag, in bl-c1b9), so the pin is
unreachable from the installed artifact alone.

## Suggested fix

In the adapter-spawn path, distinguish `ErrorKind::NotFound` from other spawn
errors and render it in the guard's voice, naming the resolved target:

```
lernie prompt: provider adapter "bz" not found on PATH (§4.4 — install the pinned binary: cargo install brazen --version =0.0.4, or set `adapter:` in <config-root>/models.yaml)
```

The pin string is already available at that point: `crate::prompt::brazen_pin()`
(`src/prompt/mod.rs:104`) is the same reader `check_bz_version`
(`src/prompt/resolve.rs:278`) uses.

## Severity

Defect. A promise-bearing surface (US-24 "actionable message") degrades to a
raw errno on the one path a stranger is guaranteed to take, and the docs'
remedy is reachable from nowhere the user is standing.

Filed by an outside evaluation pass (wharfinger) walking 0.0.1 from the public
docs only; not claimed, not fixed.
