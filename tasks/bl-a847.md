Deliverable: `docs/ARCHITECTURE.md` §2.3 edits closing the open questions below, then implementation balls. Living document.

## Status

`docs/ARCHITECTURE.md:178` (§2.3 Shipped-state note): *"The shipped harness still carries the pre-transcript shape this amendment retires: the step loop folds assistant events into an in-memory accumulator and assembles `tool_result` blocks from `tools/<tool-id>/output.json` (see README). This section is the target contract; building the transcript writer and re-pointing the assembler is implementation work tracked separately."*

It was **not** tracked separately. This is that ball.

The gap this closes is stated at §2.3:176: *"a crashed chain could not rebuild its history without either violating the contract or having held that history in RAM — and both arms fail `docs/PRINCIPLES.md` Disk-first. Now the history has exactly one home, and it is a commit."*

## Why this is a design ball

§2.3 is written, but three seams are asserted rather than specified:

**1. "One pass, two sinks."** §2.3:185 requires the executor to write assistant output *"from the adapter stream it is already consuming — one pass, two sinks (the diagnostic `response.json` and the transcript), no read-back."* But the transcript entry is committed *"when the model call settles complete"*, while `response.json` is appended live across attempt segments and its fd is held open for the whole call (§4.4:624). One stream, two sinks with different lifetimes and different commit points. Specify it.

**2. Retry and pause.** *"a retried or paused model call commits only the authoritative content"* (§2.3:185) — the last-segment-authoritative rule (§4.4). Where does the writer buffer the non-authoritative segments if not in RAM, given Disk-first is the whole point?

**3. Interleaving with delivery commits.** The `NNN` counter is one per-branch sequence shared across origins, *"assigned at commit time by the executor"* and *"derived, never stored: the next number is max-present-plus-one from a directory listing"* (§2.3:180). Delivery commits (§2.11) draw from the same counter at step boundaries. Confirm no race — the executor lock should make this trivially safe, but it interacts with the inbox ball and should be stated once, in one place.

## In scope

- The three seams above.
- The writer: `messages/NNN-assistant.json` (canonical content blocks verbatim, §4.4), `messages/NNN-tool.json` (canonical `tool_result` block, committed by the tool executor as it resolves, §3.3).
- Re-pointing the context assembler at the read-state commit’s tree — readdir + sort, no git-log walk, no index (§2.3:180).
- Deleting the in-memory accumulator and the `tools/<tool-id>/output.json` assembly path.

## Out of scope

- The inbox / delivery commits — that ball is the §2.11 substrate design. This one owns *self-output*: §2.3:190, *"Self-output commits directly; the inbox is the on-ramp for everyone else."*
