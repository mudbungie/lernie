## Verified gap
VISION (yog docs/VISION.md §4.7) verbatim: sensors ride "whatever transport (Slack MCP today) the deployment chooses" — but nothing in the suite speaks MCP. External tools are `lernie-tool-<name>` binaries on a resolved path (ARCH §3.3); none ship. The fleet demo (~/ops/fleet) used MOCK Slack tool triples. Codex meanwhile has a full MCP client (codex-rs/rmcp-client): stdio + streamable-HTTP transports, OAuth login with a token store — and its whole integration ecosystem (Slack, issue trackers, browsers) arrives through that one seam.

## Deliverable
One adapter binary that fronts a configured MCP server and projects its tools into lernie's tool declaration surface: config names the server + transport; the binary handles the session and translates tool schemas/calls. Credentials live with the adapter (brazen-style: the wire owner keeps its own credstore), never in lernie core.

## Constraints
- Zero lernie-core change; the refusals hold (no new primitives — this is an external tool like any other).
- Placement is open: in-repo under a tools/ dir, or a sibling crate. Decide in this ball; the layer law (mechanism sinks) and the extraction ledger (§6/G11) are the tiebreakers.
- Start with stdio transport (covers most servers incl. Slack MCP); HTTP/OAuth only when a real deployment needs it — no capability theater.
