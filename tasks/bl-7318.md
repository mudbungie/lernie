- run 15, load 70.6 — `prompt::tests::parent_revival::a_child_final_response_revives_the_parent_which_delivers_and_steps`: `assertion failed: matches!(out, AdvanceOutcome::Terminal)`.
- run 12, load 74.0 — `prompt::tests::verifier_gate::a_verifier_gates_a_workers_return_end_to_end_config_only`, panic message **`AlreadyDriven`** (that test already prints the outcome). That message is the whole diagnosis: the hop's `try_acquire` on its own branch's inbox returned `None`.

bl-9c06's LERNIE_HOME fix was therefore NOT the cause — neither test reads that env — and the family is wider than the two named on this ball (verifier_gate is the same shape).

## Root cause: the lease was released by closing an fd, and every spawn transiently duplicates it

`src/prompt/inbox/lock.rs` held the ARCH 2.11 lease as `flock(LOCK_EX|LOCK_NB)` on the inbox-directory fd and released it by dropping the `File` — i.e. by closing one fd. An `flock` lives on the **open file description**, and closing one fd naming it releases the lock only once **every** fd naming it is gone. `fork`/`clone` copies the whole fd table and close-on-exec fires at `execve`, not at the fork, so between any `Command::spawn` anywhere in the process (git, `bz`, a tool, a detached launch) and that child's exec, an unrelated process holds the lease too. A lease released inside that window stays kernel-held until the unrelated child execs; the next probe reads `EWOULDBLOCK` and the caller concludes *another executor drives this branch*. That lie turns a driver into a silent no-op (2.11 Writer/driver totality) and a silently-dead agent into a live one (section 8).

Both named tests match exactly:

- **parent_revival** — `dispatched_child()`'s `child_dispatch` deposits the front-door message and probes the child's inbox (acquire + release); `advance_child` then acquires that same inbox. A sibling test's spawn in the window makes the second acquire read held, so `run` returns `AlreadyDriven` before delivering anything — not `Terminal`.
- **sweep_deposits_died** — `scan` probes each branch's inbox (`is_driven`, acquire + release) and the flush then probes the parent's inbox again. A spurious hold empties `report.swept` / `report.flushed` / `launcher.invocations()`.

Measured directly with a standalone probe (4 threads acquiring+releasing on their own private dirs, 6 threads spawning `/bin/true`):

| release strategy | spurious "already driven" |
|---|---|
| close the fd (shipped behaviour) | **5,708,136 / 12,322,458 rounds (46%)** |
| explicit `flock(LOCK_UN)`, then close | **0 / 10,910,452** |
| fcntl POSIX record lock | 0 / 9,613,768 |

fcntl record locks are the other fork-immune primitive and were rejected: they are process-associated, so two open file descriptions in one process would stop contending — destroying the in-process mutual exclusion the suite legitimately uses to stand in for a rival executor (`a_driven_child_is_never_swept`, `a_parent_with_a_held_lease_gets_no_second_driver`, every AlreadyDriven arm), and requiring a lease file on disk that 2.11 deliberately does not have.

## The fix — one place, no semantic change

`ExecutorLock` gains a `Drop` that issues `flock(fd, LOCK_UN)` before the fd closes. `LOCK_UN` clears the lock from the open file description itself, so every duplicate of it loses the lease at once: release becomes exact instead of "whenever the last duplicate happens to go away". Same primitive, same in-process contention, same kernel-release-on-death, still nothing written on release. The section 6 exec baton is untouched — it `mem::forget`s the guard immediately before exec, so `Drop` never runs on the handoff path.

New test `prompt::inbox::tests::lock::release_frees_the_lease_while_a_subprocess_still_holds_its_fd` makes the transient window permanent and observable instead of raced: close-on-exec is cleared so the spawned child keeps the inherited fd for its whole life, and the child lives until the test closes its stdin. No timing verdict anywhere. Verified to have teeth — it fails on the unmodified `Drop` body and passes with it.

Docs: ARCHITECTURE 2.11 (*The executor lock*) now states that a voluntary release is an explicit `LOCK_UN`, never a bare close, and why. Section 6 (*The exec baton carries the lease*) corrects the claim that restoring close-on-exec keeps the lease out of the tool and adapter subprocesses — it keeps it out of their **exec'd images**, not out of their pre-exec window, which is exactly why release must be explicit.

Also landed: `assert!(matches!(out, AdvanceOutcome::Terminal), "{out:?}")` in parent_revival, so a future flake there names the outcome the way verifier_gate already did.
