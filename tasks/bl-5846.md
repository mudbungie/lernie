## Concern
The workspace-wide startup scan (§2.11) runs at every driver invocation — with the §6 exec baton, every hop of every chain re-sweeps every branch, and the scan's inbox flush launches drivers that themselves scan. Frequency is matched to step rate; the events it compensates for happen at crash rate. O(branches) per spawn, driver-launching-driver recursion.

## Baseline: the minimal design carries normal operation (user-confirmed)
The front door alone is self-propagating: `lernie message` (1) deposits, (2) probes the executor lock, (3) launches a driver if quiescent; the executor drains its inbox at every step boundary. Deposit-before-probe ordering means a queued item exists before anyone checks. Every terminal event deposits (§2.3 step 5 is total), so the healthy path needs zero scanning and zero inbox-watching.

## Exit protocol: the self-directed launch (user design 2026-07-12; supersedes release-then-list)
The graceful-exit crack (a deposit landing after the executor's last drain but before its lock release gets a lock-held writer probe AND a never-looking-again executor) is closed by an unconditional exit-time launch, not a conditional post-release list.

**One terminal sequence, no agent kinds** (user-confirmed): reach final response → deposit result/epitaph into the parent's inbox (**a structural no-op for a parentless agent** — already how `inbox::deposit_child_result` ships, §2.6 note; the deposit is executor-side and never consults the agent, PRINCIPLES 'Return is not a verb') → release own lock → spawn a driver at own agent, fire-and-forget → exit. The only conditional is 'does a parent inbox exist', derived from the id (§2.3). A user reprompt and a parent's message are the same deposit (§2.11: every sender indistinguishable from a user); parent/child is provenance, not a category (§2.1).

Governing symmetry: **no launcher ever decides whether launching is warranted; warrant is decided by the launched driver under the lock.** Writers already work this way; the exit launch is the same act with the sender's own agent as target — same act, same name, no new noun. Invariant: after release, the exiting process has no authority — spawn and exit are its only remaining acts (dissolves the dual-processing reverse race: the new lock-holder is the sole writer from acquire).

**Terminology (settled 2026-07-12):** the existing spec term **revive** stands for launch-anew (§2.3 step 6, §2.5 'revival-on-deposit'); bury/exhume dropped (poetic flourish, no TAXONOMY addition). Earlier drafts used 'burial' with inverted polarity; retired.

Two pins:
1. **No-op driver path** (needed anyway for racy launches): a driver that acquires and finds nothing to deliver on a terminal branch exits silently — no step, no epitaph, no further launch. This structurally terminates the recursion: found-mail → step to a new terminal → exit-launch again (normal lifecycle); found-nothing → nothing relaunches.
2. **Exit-launch by epitaph value** (§2.6: branch on value, never shape): final response → launch; `stopped` → never (relaunch would resurrect the branch the operator just killed — pre-stop mail waits for the next explicit touch; future deposits still revive per §2.9); `budget-exhausted` → never (drain→exhaust→deposit epitaph-spam cycle against a hard ceiling).

Cost: one no-op spawn per normal termination — termination frequency, not step frequency. Accepted at current scale (user 2026-07-12); optimize later only if measurement shows it. Spawn failure falls into the accepted crash class below.

inotify is NOT a correctness mechanism anywhere in this: holding the fd confers no notifications and inotify queues overflow; it may serve as a mid-loop latency optimization only (same advisory status as §3.1 frontend watching). The authoritative read is the drain's readdir under the lock.

## Crashes: accepted as a failure class (user decision 2026-07-12)
Uncatchable death (SIGKILL/OOM/panic/reboot) strands (a) a dead child's undeposited result — parked parent waits until next touch; (b) messages deposited while the doomed executor lived. Decision: treat crashes as crashes. Everything is on disk, so nothing is lost, only late; the next touch heals (a user reprompt, or `lernie scan` run by hand / cron if an operator wants a heartbeat). Rationale: auto-healing exacerbates the worst failure modes — a janitor relaunching the runaway agent an operator is trying to kill. The janitor verb is an OPERATOR tool, never wired into any hot path or default schedule.
