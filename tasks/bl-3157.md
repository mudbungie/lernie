## The bug
`claude-sonnet-4-7` is not a real model id — the Sonnet line is 4.0 → 4.5 → 4.6 → 5; there is no 4.7. It is the **worker** role's model in `template/providers.yaml`, which every `lernie new` copies into a workspace's first config commit. The default role for all real work would 404 on its first `bz` call. Valid current Anthropic ids: `claude-sonnet-5`, `claude-sonnet-4-6`, `claude-opus-4-8`, `claude-haiku-4-5` (the compactor's `claude-haiku-4-5` is correct).

## Why it was never caught
No live model call has ever been made. Every 'shipped' claim rides tests that mock the wire (`tests/prompt_end_to_end.rs` points `bz` at an httpmock Anthropic SSE endpoint). The only workspace on disk (`~/.local/share/lernie/workspaces/1f07690d`) has one commit and an empty `steps/`. This is the first bug of the class 'only exists because the wire has never been real' — expect siblings on the first real run.

## Where it lives (SSOT violation — 4 homes of the same string)
1. `install/models.yaml` — the `models:` entry (capabilities + context_window)
2. `template/providers.yaml` — worker role `model: claude-sonnet-4-7`
3. `docs/ARCHITECTURE.md` §4.2 and §4.3 — both code-fence examples use it
4. ~20 test fixtures under `src/prompt/tests/`, `src/config/`, `tests/` (grep `claude-sonnet-4-7`)

## Fix (mechanical part)
Replace with a real id (recommend `claude-sonnet-5` for the worker) across all four homes. Tests that only need *a* declared id can keep using a fixture id, but the shipped `install/models.yaml` + `template/providers.yaml` must name a model that actually resolves on the wire, and the ARCH examples must not teach a fake id.

## The real question the user raised: why hardcode a model at all?
Today the model id is a hand-authored string in `models.yaml` (capabilities lernie acts on) that a role references by id in `providers.yaml`, cross-validated at load by `src/config/cross/roles_check.rs`. Nothing validates the id against what the provider actually serves — which is exactly how a fake id shipped. But `bz --list-models [--provider <id>]` exists and enumerates the provider's real catalog (verified: it returns live model lists). Open design question for this ball, settle with the user before the mechanical fix lands as doctrine:
- `models.yaml` is deliberately NOT a mirror of the provider catalog (ARCH §4.2: 'lernie performs no model-list calls of its own; models.yaml carries only the facts lernie acts on'). That's a defensible SSOT stance — capabilities are lernie's fact, the catalog is brazen's.
- But the *id* is brazen's fact, and we hand-copy it into lernie config with no check. The severable options: (a) leave as-is, accept that a wrong id fails loudly at first call (arguably fine — brazen owns id validity, §4.2); (b) add an optional `lernie` verb or `bl`-time check that reconciles `models.yaml` ids against `bz --list-models`; (c) let a role name a *capability profile* rather than a concrete id and resolve the newest matching id from `bz --list-models` at author time.
- Recommend (a) as the shipped default (matches §4.2's stance — id validity is brazen's, fail loud on first call) plus documenting that a live `lernie prompt` is the required smoke test after `lernie new`. (b)/(c) are severable enhancements, not blockers. Confirm with user.
