## Scope
The platform's stated purpose — "Experiments are config diffs, measurable against a task suite" (§1 Testability) — is unmeasurable today. Three deliverables, roughly in order:
1. Bundle/replay (§9.2): archive an agent subtree as one git bundle (branch + descendants, ancestry back through the governing config commit) plus the steps/ and inbox/ diagnostic slices; replay = clone into a scratch workspace under LERNIE_HOME, restore slices, inspect with the ordinary frontend. Replay is not a mode (§2.3) — this is mostly plumbing plus a verb.
2. Task suite (v0.9): 50 tasks with machine-checkable success criteria, ≥10 per failure category (early termination, scope reduction, skipped tests, hallucinated APIs, error recovery, fabricated success, context hygiene), per-category tagging.
3. Runner (v0.10): agent-eval --config <experiment> --suite <suite> --runs N → per-task pass@1 (mean-of-means, Wilson 95% CI) and pass@5. Experiments are workflow.yaml variants (§9.3), no code changes.

## Open decisions (user)
- Runner home: the spec names a separate binary (agent-eval); a lernie subcommand would fit CLI-as-control-plane but bloats the core with experiment-driver concerns. Recommend separate binary in this repo's workspace (crates/agent-eval).
- Suite home: in-repo (tests/suite/) vs its own repo. In-repo keeps experiments and suite versioned together; own repo keeps the harness repo lean.

## Sequencing
No claim blockers: bundle/replay and suite authoring are independent of the other epics; the runner only becomes meaningful once workflow variants exist (bl-6a3b).
