## The defect

`template/providers.yaml`, shipped and embedded via `include_dir!`:

    roles:
      worker:
        provider: anthropic
        model: claude-sonnet-5
        tools: [bash, read_file, load_skill]
      compactor:
        provider: anthropic
        model: claude-haiku-4-5

The install's tool pool (`schemas/tools/`, `skills/`) ships **five** tools:
`bash`, `dispatch`, `load_skill`, `message`, `read_file`. The worker row grants
three. `message` and `dispatch` are granted to nobody.

ARCH §4.3: *"A root records no role and resolves the `worker` default — roots
are workers"*. So **every root/interactive conversation in every workspace this
harness creates is capped at `[bash, read_file, load_skill]`** and structurally
cannot message a sibling or dispatch a child, whatever it is asked to do.

Confirmed on the wire in yog bl-bd9d: `steps/<id>/006/request.json` `tools` ==
`["bash","read_file","load_skill"]`. The model's refusal was **correct**; the
operator read it as "the model can't use its tools", which cost three user
turns on the first incident and five wasted steps on the second.

## Why it is a defect and not minimalism

The three-name subset has no principle behind it. It is drift: `load_skill` was
added to the row when that tool shipped; `message` and `dispatch` were not, and
nothing enforces the correspondence. The pool is the install's own declaration
of what it provides; the shipped default role should grant it, and narrowing is
an operator config edit (severability — removing a default deletes config, not
code).

## Deliverable

1. `template/providers.yaml` worker row grants the whole shipped pool.
2. A test that makes the drift impossible again: the template's worker `tools:`
   must equal the `schemas/tools/` pool, by name. Scrutiny, not mechanism —
   the list stays authored, visible and overridable.

## Landed

- `template/providers.yaml` — worker grants `[bash, dispatch, load_skill,
  message, read_file]`; header comment states why the grant is the whole pool
  and where narrowing belongs. Compactor row left empty with the reason beside
  it.
- `src/install/tests.rs::the_shipped_worker_grant_is_the_whole_tool_pool` — the
  drift guard: the embedded template's worker `tools:` must equal the embedded
  `schemas/tools/` pool, by name; the compactor's must be empty.
- `docs/ARCHITECTURE.md` §4.3 **Toolset** — records the shipped grant, the
  drift it replaces, and that the correspondence is a test rather than a
  runtime derivation (the list stays authored, so narrowing stays severable).

### Two blockers cleared on the way (main was red before this task)

Neither is this defect; both had to be fixed for any close to pass the gate.

1. **The suite borrowed the operator's `~/.gitconfig`.** A machine-global
   `core.hooksPath` gained a `commit-msg` hook enforcing the operator's own
   author identity, so every test that commits with a synthetic identity
   (`user.email=t@t`, `GIT_AUTHOR_EMAIL=test@example.invalid`) was refused —
   39 failures in one run, in a voice indistinguishable from a code
   regression. Fixed the same way, and for the same stated reason, the
   Makefile already isolates `bz`: the test recipes now run git against a
   generated `target/test-gitconfig` (identity only) with
   `GIT_CONFIG_SYSTEM=/dev/null`. Test recipes only — `install`, `smoke` and
   anything a user runs are untouched.
2. **`tests/commit_hygiene.rs` red on main's own tip.** The PR #2 merge
   (`ceee487`) was made through GitHub's web UI, which authors as the account
   *profile* name (`Mud Bungie <mudbungie@gmail.com>`) and commits as `GitHub
   <noreply@github.com>`. The guard matched the owner as a (name, email) pair
   and allowed no web-UI committer, so it failed on a legitimate merge. It now
   matches the owner by **email** — the identity; the display name is not
   under local control — and allows `noreply@github.com` as the same class of
   GitHub-minted machine identity `github-actions[bot]` already was.
